# CLAUDE.md

## О проекте

Учебный и портфолийный проект: система проката инструмента. Next.js 16 (App Router, `--src-dir`) + Supabase.

Главная тема - RBAC и RLS на уровне Postgres. Права задаются грантами и политиками в базе. Проверки на фронте нужны только для удобства интерфейса и никогда не заменяют проверку в базе.

Репозиторий должен читаться как учебник. Человек, открывший его через полгода, проходит `docs/book/` и миграции по порядку и может повторить проект с нуля, понимая каждую строку SQL. Поэтому качество комментариев и документации - требование того же уровня, что и работающий код. Изменение, где код работает, а комментарии и книга не обновлены, не считается сделанным.

**Статус: все этапы плана (0-8) закрыты.** Проект в режиме сопровождения: исправления, рефакторинг, точечные доработки. Итог каждого этапа - в `docs/progress.md`, выводы - в `docs/rls-notes.md`.

ТЗ лежат в `docs/tz/`:
- `tz-source.md` - исходный запрос заказчика с фриланс-биржи (контекст, не план);
- `tz-plan.md` - план этапов 0-8, по которому проект построен. Новых этапов в нём нет.

`tasks/` - архив заданий этапов, в репозиторий не входит (исключён через `.git/info/exclude`). Нужен, только если требуется понять, почему в прошлом этапе решили так. Главы книги и остальные документы в `docs/` на него не ссылаются. Если новая доработка приходит отдельным заданием, оно кладётся туда же (`tasks/NN-<slug>.md`, номер продолжает нумерацию).

## Стек и структура

- Next.js 16, TypeScript, Tailwind, shadcn/ui (на Base UI). Сессия обновляется в `src/proxy.ts`.
- `@supabase/ssr`. Клиенты в `src/lib/supabase/`:
  - `server.ts` - сессионный клиент для серверных компонентов, server actions и route handlers. Запросы идут от имени пользователя, RLS работает. Основной клиент.
  - `client.ts` - браузерный клиент. Используется для загрузки файлов напрямую в Storage.
  - `admin.ts` - secret key, обходит RLS. Только скрипты и seed. В коде приложения не использовать: если кажется, что без него не обойтись, остановись и спроси. `npm run check:bundle` ловит утечку ключа в бандл.
- Раскладка по фичам: `src/features/<feature>/` - `queries.ts`, `actions.ts`, `types.ts`, `constants.ts`, компоненты фичи рядом. Фичи: `tools`, `customers`, `rentals`, `pricing`, `audit`, `dashboard`, `import`, `staff`. Общий UI - `src/components/ui/`.
- Общие хелперы в `src/lib/`: `roles.ts` (`hasRole` - только UX), `format.ts` (деньги и даты), `db-errors.ts` (перевод ошибок Postgres в текст интерфейса), `random-name.ts` (имена файлов без `crypto.randomUUID`), `form-data.ts`.
- Страницы: `src/app/(app)/` - за сессией, `src/app/(auth)/login`, route handler импорта - `src/app/api/import/tool-units`.
- Типы БД: `src/types/database.ts`, генерируются после каждой применённой миграции: `npm run db:types`.
- Тестовые пользователи (`operator@`, `manager@`, `admin@example.com` и деактивированный `inactive@example.com`) и образцы инструмента создаются `npm run seed:staff` (`scripts/seed-staff.ts`, Admin API). Сид идемпотентен, повторный запуск безопасен.
- Навигация задаётся массивом в `src/components/layout/nav-config.ts`. Новый раздел приложения - новая строка в этом массиве с иконкой `lucide-react` и минимальной ролью. Скрытие пункта по роли - UX, доступ держат политики.

## Язык

Приложение называется **Tool Rental**.

**На английском:**
- весь текст интерфейса: меню, заголовки, таблицы, формы, кнопки, подписи статусов и категорий, пустые состояния, сообщения об ошибках;
- тексты ошибок в новых SQL-функциях и триггерах (`raise exception '...'`);
- `README.md`, `docs/policy-matrix-report.md`, тексты `description`/`why` в `tests/api/matrix.ts` - то, что видит посетитель репозитория;
- сообщения коммитов (Conventional Commits).

**На русском:**
- все комментарии в коде: миграции, SQL-тесты, TypeScript;
- `comment on table` / `comment on column`;
- книга `docs/book/`, `docs/rls-notes.md`, `docs/roles.md`, `docs/progress.md`.

Задания пишутся по-русски, и примеры текстов интерфейса в них тоже русские ("единица уже выдана"). В код они попадают переведёнными на английский.

Библиотеку i18n не подключать: второго языка не планируется, строки пишутся прямо в компонентах. Подписи значений enum (статусы единиц, категории клиентов, роли) - в `constants.ts` соответствующей фичи, одним словарём на enum.

Форматирование чисел, денег и дат - только через `src/lib/format.ts`, локаль `en-GB`, валюта UAH.

Ранние миграции содержат русские тексты ошибок. Миграции не переписываются: интерфейс различает ошибки по SQLSTATE и имени ограничения (`src/lib/db-errors.ts`) и показывает свой английский текст, а не `error.message` из базы.

## Окружение

База - облачный проект Supabase, привязанный к репозиторию через `supabase link`. Локального стека нет: Docker не используется, `supabase start` не запускать. Код (Next.js, CLI, скрипты) работает локально.

Команды - только через скрипты `package.json`:

| Скрипт | Что делает |
|---|---|
| `npm run db:new <name>` | создаёт пустой файл миграции в `supabase/migrations/` |
| `npm run db:push` | применяет к облачной базе миграции, которых там ещё нет |
| `npm run db:types` | генерирует `src/types/database.ts` по облачной схеме |
| `npm run db:reset` | **пересоздаёт облачную базу**: удаляет все данные, включая пользователей Auth. Запрещён без прямой просьбы |
| `npm run seed:staff` | создаёт тестовых сотрудников и образцы инструмента через Admin API |
| `npm run test:sql` | все SQL-тесты из `tests/` по порядку имени файла, остановка на первом `FAIL` |
| `npm run test:api` | матрица прав через настоящий API (5 участников), перезаписывает `docs/policy-matrix-report.md` |
| `npm run test:all` | `test:sql` + `test:api` |
| `npm run check:bundle` | `next build` и поиск секретов в `.next/static` |

`test:sql` идёт через `psql` (`DB_URL` из `.env.local`), а если `psql` не установлен - через `supabase db query --linked -f`, тогда без построчных `NOTICE`. Один файл вручную:

```bash
set -a; source .env.local; set +a
psql "$DB_URL" -v ON_ERROR_STOP=1 -f tests/policies/04_rentals.sql
# без psql:
npx supabase db query --linked -f tests/policies/04_rentals.sql
```

Раннер пропускает `tests/manual`, `tests/fixtures`, `tests/api`. Файлы в `tests/manual/` запускаются только руками и только по прямой просьбе: `break-policy.sql` намеренно ломает политику в облачной базе, после него обязателен `restore-policy.sql`.

`db:push`, `db:reset`, `seed:staff`, `test:api` и psql пишут прямо в облачную базу, другой базы нет. `test:api` создаёт данные с префиксом `__matrix-`, остаток убирает `tests/manual/cleanup-matrix-data.sql`. Отката у `db:push` нет: применённую миграцию исправляют новой (исключение для идемпотентного SQL - в разделе "Порядок работы"). Поэтому SQL применяется только в фазе 2 и только после явного "применяй".

| 5 | `category_grace_periods`, снимки `grace_hours` / `daily_rate`, `calc_rental_amount()`, RPC `rental_estimate()` | `05_calc.sql`, `05_pricing.sql` | `05-pricing.md` |

| 8 | грант DELETE на `tool_units` (найденная дыра), матрица через API | `08_tool_units_delete.sql`, `tests/api/` | `08-policy-matrix.md` |

Ключевые решения, которые не пересматриваются без обсуждения:
- роль хранится в таблице `staff`, не в JWT: деактивация действует со следующего запроса;
- в политиках функция роли вызывается как `(select public.current_staff_role())`: обёртка в `select` превращает вызов в initplan, функция выполняется один раз на запрос;
- статус `tool_units` - производная от `rental_items`, а не флаг; выдача и возврат - RPC `security invoker`;
- тариф и grace - снимки в момент создания строки, суммы задним числом не меняются;
- файлы в Storage неизменяемые (нет политик UPDATE и DELETE), показ через signed URL на 60 секунд, создаётся сессионным клиентом;
- аудит пишется только триггером, политик на запись в `audit_log` нет.

## Особенности окружения, которые легко забыть

1. **Авто-гранты при создании таблиц отключены.** Каждой новой таблице, последовательности и представлению нужны явные `GRANT` для `authenticated`, а если с объектом работают скрипты - и для `service_role`. У `service_role` есть `BYPASSRLS`, но это обход политик, а не грантов. Без гранта запрос падает с `42501` раньше, чем дело дойдёт до политик. Обратная ловушка (этап 8): политика без гранта не срабатывает никогда - новая политика требует проверить, что грант на эту операцию есть.
2. **Postgres по умолчанию даёт `EXECUTE` на новую функцию роли `PUBLIC`**, то есть в том числе `anon`. Для каждой функции: `revoke execute ... from public`, затем `grant execute` нужным ролям.
3. **`security definer` без `set search_path` запрещён.** Всегда `set search_path = ''` или `= public` и полные имена объектов в теле.
4. **Телефон в локальной сети открывает dev-сервер по HTTP** (`http://<IP компьютера>:3000`, в `next.config.ts` задан `allowedDevOrigins`), это не secure context. `crypto.randomUUID()` и камера через `getUserMedia` там недоступны и падают молча. Для имён файлов - `randomName()` из `src/lib/random-name.ts`. Для фото - `<input type="file" accept="image/*" capture="environment">`, он работает и без secure context. Для QR-наклеек с телефона - `NEXT_PUBLIC_APP_URL` с адресом компьютера в сети.
5. **Время ставит база.** `issued_at`, `returned_at` и подобные поля не принимаются от клиента: их заполняет `default now()` или триггер. Иначе оператор может задним числом убрать просрочку.
6. **Каждая новая таблица попадает в аудит.** Триггер `audit_<table>` на `audit_log_row()` добавляется в той же миграции, что и таблица.

## Порядок работы

Любое изменение схемы или политик идёт в две фазы. Правки только в интерфейсе, документации или скриптах - без фаз, но с проверкой из шага 2 фазы 2.

**Фаза 1. SQL и тесты. Ничего не применять.**

1. Прочитать задание или запрос, миграции затронутых таблиц, их тесты, `docs/rls-notes.md`, главы книги затронутых этапов.
2. Написать миграции (`npm run db:new <name>`), SQL-тесты, черновик текста для книги (см. "Книга").
3. Остановиться и выдать отчёт:
   - список созданных файлов;
   - решения, которые отличаются от запроса или которых в нём нет, с причиной;
   - что проверить руками, как чек-лист.

**Фаза 2. Только после явного "применяй".**

1. Применить миграции: `npm run db:push`.
2. Прогнать `npm run test:all`. Упал старый тест или ячейка матрицы - это регрессия, остановиться и сообщить.
3. Сгенерировать типы: `npm run db:types`.
4. Сделать интерфейс. `npx tsc --noEmit`, `npm run lint`, `npm run build` - без ошибок. Если менялись переменные окружения, клиенты Supabase или импорты `admin.ts` - `npm run check:bundle`.
5. Обновить документы (см. "Остальные документы").
6. Предложить сообщение коммита (Conventional Commits, английский). Не коммитить.

**Изменились права** (политика, грант, новая таблица или RPC, доступная приложению) - в той же задаче обновить `tests/api/matrix.ts`, перегенерировать отчёт через `npm run test:api` и таблицу "Permission matrix" в `README.md`, `docs/roles.md`. Матрица, которая не знает о новом праве, его не проверяет.

**Если после применения что-то не так.** По умолчанию исправление - новой миграцией. Исключение, только с согласия: если SQL в применённом файле идемпотентен (`grant`, `create or replace function`, `drop policy if exists` + `create policy`), файл можно исправить и отправить повторно:

```bash
npx supabase migration repair --status reverted <версия>
npm run db:push
```

`repair` только снимает отметку о применении в истории миграций облачной базы, сам SQL не откатывает. Поэтому повторное выполнение безопасно лишь для идемпотентного SQL. `create table` и миграции данных так не переписываются никогда.

**Никогда:** менять схему через Studio; выключать RLS на таблице, даже временно; писать политику на запись с `using (true)` или `with check (true)`; импортировать `admin.ts` в код, который может попасть в клиентский бандл; запускать `npm run db:reset`, `supabase start` или `supabase db reset` без `--linked`; запускать `db:push` в фазе 1; запускать `tests/manual/break-policy.sql` без прямой просьбы.

## Стандарт комментирования SQL

Это главное требование проекта. Комментарии пишутся для читателя, который знает SQL и Postgres, но видит Supabase и RLS впервые и читает файл без внешних объяснений.

Общие правила:
- язык - русский; только дефис `-`, длинное тире `—` не использовать;
- комментарий объясняет **почему** и **что сломается без этого**, а не пересказывает код. Плохо: `-- создаём индекс по tool_unit_id`. Хорошо: `-- Одна единица не может быть одновременно в двух активных арендах...`;
- ширина строки комментария - до 80 символов;
- каждая новая механика (то, чего не было в прошлых миграциях) при первом появлении объясняется подробно, со ссылкой на главу книги: `-- Подробно: docs/book/04-rentals.md, раздел "Частичный индекс"`. При повторном использовании - одна строка;
- миграция делится на пронумерованные секции в порядке чтения, у каждой секции заголовок-разделитель.

### Шапка миграции

```sql
-- =====================================================================
-- Этап 4. Аренда: выдача и возврат (часть 1 из 2)
--
-- Что делает:
--   Таблицы rentals и rental_items, запрет двойной выдачи единицы,
--   синхронизация статуса tool_units триггером.
--
-- Зависит от:
--   <файл миграции> - tools
--   <файл миграции> - staff, current_staff_role()
--   <файл миграции> - customers, customer_category
--
-- Новое в этой миграции (подробно в docs/book/04-rentals.md):
--   частичный уникальный индекс; security definer в триггерной функции;
--   инвариант "статус единицы следует из данных", а не из флага.
--
-- Как проверить:
--   psql "$DB_URL" -f tests/policies/04_rentals.sql
-- =====================================================================
```

### Политика

Над каждой политикой:
- какая роль, какая операция;
- что проверяет `USING` (существующая строка: какие строки видны или какие можно менять);
- что проверяет `WITH CHECK` (записываемая строка: какой может стать строка после записи);
- почему именно так и какой очевидный вариант не подошёл;
- **негатив**: какая роль каким запросом получает пусто, 0 строк или `42501`.

Образец уровня (из миграции этапа 3):

```sql
-- INSERT в storage.objects = загрузка файла (upload без upsert).
-- WITH CHECK проверяет строку метаданных загружаемого файла:
--   bucket_id - политики storage.objects общие для всех бакетов
--     и объединяются через OR. Без этого условия политика открыла бы
--     загрузку в любой бакет, включая бакет фото аренд этапа 4.
--   current_staff_role() - загружает только активный сотрудник.
--   exists - первая папка пути является id клиента. Подзапрос идёт
--     через RLS customers: клиент должен быть виден вызывающему.
-- UPDATE и DELETE политик нет: файлы неизменяемые.
-- Негатив: оператор загружает 'photo.jpg' (корень) или
--   '<несуществующий uuid>/photo.jpg' - 42501;
--   залогиненный без строки в staff - 42501.
```

### Функция

- зачем она и кто её вызывает (RPC из приложения, политика, триггер);
- `security definer` или `security invoker` и почему. Для `definer` - какие именно права она получает и почему это безопасно;
- `immutable` / `stable` / `volatile` и почему;
- зачем зафиксирован `search_path`;
- кому выдан `execute` и почему отозван у `public`;
- какие ошибки бросает (SQLSTATE и текст), чтобы интерфейс мог их различать.

### Триггер

- `before` или `after`, на какие операции и колонки (`update of ...`), `for each row` или `statement`;
- какой инвариант держит;
- что сломается без него, конкретным сценарием;
- если на таблице несколько `before`-триггеров: они срабатывают в алфавитном порядке имён. Указать, от какого порядка зависит корректность.

### Ограничения, индексы, гранты

- у `check`, частичных и уникальных индексов - какое правило домена защищают и какую ошибку получит нарушитель;
- гранты на уровне колонок: почему именно эти колонки и какие намеренно исключены;
- `comment on table` для каждой таблицы, `comment on column` для неочевидных колонок (снимки цен, пути к файлам, служебные поля). Эти описания видны в Studio.

### SQL-тесты

Формат как в `tests/policies/02_roles.sql`:
- шапка: этап, что проверяется, предусловия, как запустить (SQL Editor и psql);
- всё внутри `begin; ... rollback;`, хелперы `pg_temp.act_as(email)`, `pg_temp.act_as_anon()` и проверка ожидаемой ошибки по SQLSTATE;
- каждая проверка - комментарий: роль, действие, ожидание (разрешено / пусто / 0 строк / ошибка с кодом) и какая политика или ограничение это обеспечивает;
- на каждую политику минимум одна позитивная и одна негативная проверка;
- провал останавливает скрипт с текстом `FAIL: ...`, успех пишет `NOTICE ok: ...`.

## Стандарт комментирования TypeScript

Комментировать то, что связано с границами доступа и выполнения, остальное - по необходимости:
- какой клиент Supabase используется и почему (сессионный против admin);
- где проходит граница сервер/клиент и почему код оказался по эту сторону (`'use server'`, `'use client'`);
- проверка роли в интерфейсе - всегда с пометкой, что это UX, а защита в базе, и ссылкой на политику;
- как обрабатываются коды ошибок Postgres (`23505`, `23514`, `42501`, `P0001`) и что видит пользователь;
- JSX и очевидный код не пересказывать.

## Книга: `docs/book/`

Главы `00`-`08` написаны, по одной на этап. Оглавление - `docs/book/README.md`. Задача книги - по ней можно пройти проект заново с пустой базы, понимая, что и зачем делаешь. Глава не пересказывает миграцию построчно (это делают комментарии), а даёт картину и порядок.

Куда идёт текст при доработке:
- **исправление или мелкое изменение** без новой механики - в главу этапа, к которому относится код: раздел "Грабли" (ошибка, SQLSTATE, причина, починка) или "Решения и альтернативы", с пометкой, что это правка после завершения этапа. Старый текст не переписывается, если он не стал неверным;
- **доработка с новой механикой** - новая глава `docs/book/09-<slug>.md` (дальше по порядку) по полной структуре ниже, строка в оглавлении. Миграции и тесты такой доработки - с тем же номером (`tests/policies/09_<slug>.sql`, шапка миграции "Доработка 9. ...").

Структура главы:

1. **Задача этапа.** Какое бизнес-правило или требование реализуем, в двух-трёх абзацах.
2. **Новая механика.** Каждое новое понятие (частичный индекс, `security definer` в триггере, `security_invoker` у view, подтранзакции в plpgsql и т.д.) с нуля: что это, как выглядит, что происходит при выполнении, минимальный пример на 5-10 строк. Одно понятие - один подраздел.
3. **Порядок чтения файлов.** Нумерованный список файлов этапа (миграции, тесты, TS) в том порядке, в котором их стоит читать, и на что смотреть в каждом.
4. **Решения и альтернативы.** Какие варианты были, какой выбран, почему. Что было бы при другом выборе.
5. **Как повторить с нуля.** Команды и шаги от "миграций этапа ещё нет" до "всё работает".
6. **Как проверить.** Команды тестов, ручные проверки, ожидаемый вывод.
7. **Грабли.** Ошибки, которые возникли при разработке или легко возникают: текст ошибки, SQLSTATE, причина, как чинить.
8. **Вопросы для самопроверки.** 5-8 вопросов, ответы под `<details>`.

Разделы 1-4 пишутся в фазе 1, остальные - в фазе 2.
