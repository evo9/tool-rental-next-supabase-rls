# Матрица прав

Роли иерархичны: каждая следующая может всё, что предыдущая.

## tools, staff

| Действие | OPERATOR | MANAGER | SUPERADMIN |
|---|---|---|---|
| tools: чтение | да | да | да |
| tools: создание, изменение | - | да | да |
| tools: удаление | - | - | да |
| staff: чтение | своя строка | своя строка | все |
| staff: создание, изменение, удаление | - | - | да, кроме понижения, деактивации и удаления себя |

## customers

| Действие | OPERATOR | MANAGER | SUPERADMIN | не сотрудник | anon |
|---|---|---|---|---|---|
| читать | да | да | да | пусто | 42501 |
| создать с категорией SILVER | да | да | да | 42501 | 42501 |
| создать с другой категорией | 42501 | да | да | 42501 | 42501 |
| править имя, телефон, фото | да | да | да | 0 строк | 42501 |
| менять категорию | 42501 (триггер) | да | да | 0 строк | 42501 |
| менять id, created_at | 42501 (грант на колонки) | 42501 | 42501 | 42501 | 42501 |
| удалить | 42501 | 42501 | 42501 | 42501 | 42501 |

Категорию клиента ограничивают два разных механизма: при вставке - `WITH CHECK` политики, при изменении - триггер `customers_guard_category`, потому что политика не видит прежнее значение строки.

Удаление клиента не выдано никому: на клиента сошлётся история аренд, блокировка - это категория `NON_GRATA`, а файлы из Storage через SQL не удаляются.

## tool_units

| Действие | OPERATOR | MANAGER | SUPERADMIN | не сотрудник | anon |
|---|---|---|---|---|---|
| читать | да | да | да | пусто | 42501 |
| создать | 42501 | да | да | 42501 | 42501 |
| менять номер, статус, заметку | 0 строк (политика) | да, если переход допустим | да, если переход допустим | 0 строк | 42501 |
| удалить | 0 строк | 0 строк | да, если ни разу не выдавалась | 0 строк | 42501 |

Допустимость перехода статуса решает не политика, а триггер `tool_units_guard_status`: `WRITTEN_OFF` - конечный статус, `RENTED` возможен только при активной позиции в `rental_items`, выход из `RENTED` - только когда активной позиции не осталось. Грант и политика решают "может ли роль тронуть строку", триггер - "какой именно переход допустим" (подробно - `docs/book/04-rentals.md`).

## rentals, rental_items

| Действие | OPERATOR | MANAGER | SUPERADMIN | не сотрудник | anon |
|---|---|---|---|---|---|
| читать | да | да | да | пусто | 42501 |
| выдать (`issue_rental`) | да | да | да | 42501 | 42501 |
| принять возврат (`return_rental_items`) | да | да | да | 42501 | 42501 |
| писать `created_by`, `issued_at`, `status`, `closed_at` | 42501 (грант на колонки) | 42501 | 42501 | 42501 | 42501 |
| менять `note` у rentals | да | да | да | 0 строк | 42501 |
| удалить (`rentals` или `rental_items`) | 42501 | 42501 | 42501 | 42501 | 42501 |

`status`/`closed_at` у `rentals` и `status` у `tool_units` пишет только триггер `rental_items_sync_unit` (`security definer`) - ни одна роль, включая SUPERADMIN, не имеет на них прямого гранта. Удаление `rentals`/`rental_items` не выдано никому: история выдачи не удаляется в принципе, в отличие от `tool_units`, где SUPERADMIN может удалить единицу, которую ни разу не выдавали.

Одна единица не может быть в двух активных арендах одновременно - частичный уникальный индекс `rental_items_active_unit`, `23505` при попытке. Клиенту в категории `NON_GRATA` аренда не выдаётся - `rentals_guard_customer`, `P0001`.

## category_grace_periods, снимки тарифа и grace (этап 5)

| Действие | OPERATOR | MANAGER | SUPERADMIN | не сотрудник | anon |
|---|---|---|---|---|---|
| читать grace периоды | да | да | да | пусто | 42501 |
| менять grace периоды | 0 строк | да, в границах 0-72 | да, в границах 0-72 | 0 строк | 42501 |
| создать/удалить категорию | 42501 (нет гранта) | 42501 | 42501 | 42501 | 42501 |
| писать `rentals.grace_hours`, `rental_items.daily_rate`, `rental_items.amount` напрямую | 42501 (нет гранта) | 42501 | 42501 | 42501 | 42501 |

`category_grace_periods` ведёт себя как `tools`/`tool_units`: грант на
`update (grace_hours)` выдан любому `authenticated`, роль решает
политика - поэтому `OPERATOR` получает "0 строк", а не `42501`.
`rentals.grace_hours` и `rental_items.daily_rate`/`amount` устроены
иначе - грант на запись не выдан вообще никому, включая `SUPERADMIN`:
это снимки и итог, которые заполняют только триггеры
(`rentals_set_grace_hours`, `rental_items_set_daily_rate`,
`rental_items_set_return_amount`), приложение их не пишет ни при каких
условиях.

Тариф и grace фиксируются в момент создания строки (`rentals`/
`rental_items`) и не меняются, даже если после этого поменяли
`tools.daily_rate` или `category_grace_periods.grace_hours` - сумма уже
выданной или закрытой аренды не "плывёт" задним числом.

## rental_estimate

| Действие | OPERATOR | MANAGER | SUPERADMIN | не сотрудник | anon |
|---|---|---|---|---|---|
| вызвать `rental_estimate()` | да | да | да | пусто (RLS внутри функции) | 42501 на execute |

`security invoker`: функция не содержит отдельной проверки роли, всю
работу делает RLS вызывающего на `rentals`/`rental_items` - у
не-сотрудника соединение просто не находит строк и возвращает пустой
результат, а не ошибку.

## Общее

- Деактивированный сотрудник (`is_active = false`) не проходит ни одну политику, кроме чтения своей строки в `staff`.
- Анонимный запрос к таблицам `public` отклоняется на уровне грантов (`42501`). На `storage.objects` грант у `anon` выдан Supabase, поэтому там ответ пустой, а не ошибка.

Проверка: `tests/policies/02_roles.sql`, `tests/policies/03_customers.sql`, `tests/policies/04_rentals.sql`, `tests/pricing/05_calc.sql`, `tests/policies/05_pricing.sql`.
