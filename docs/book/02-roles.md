# Глава 02. Роли

## 1. Задача этапа

До этой главы в системе был только один уровень доступа: "залогинен /
не залогинен". Точке проката нужно больше - оператор, менеджер и
суперадмин с разным набором прав на одни и те же таблицы. Этап вводит
таблицу `staff` с ролью каждого сотрудника и переписывает политики на
`tools` так, чтобы они смотрели не на факт логина, а на роль.

Здесь впервые появляются: функция, вызываемая изнутри политики;
`security definer` и вопрос, почему он не дыра в безопасности; разница
между `USING` и `WITH CHECK`; и формат SQL-теста, который умеет
притвориться конкретным пользователем без единого HTTP-запроса.

## 2. Новая механика

### `staff`: роль в таблице против роли в JWT

Политике нужно узнать роль вызывающего. Есть два принципиально разных
источника этой информации, и проект выбрал один осознанно, отклонив
другой.

**Подход А - роль лежит в таблице `staff`** (выбран как основной).
Политика (через функцию, ниже) делает подзапрос к `staff` по
`auth.uid()`. Роль меняется мгновенно: `UPDATE staff SET role = ...`
действует со следующего же запроса, перелогин не нужен. Цена - каждый
запрос к защищённой таблице тянет за собой дополнительное чтение
`staff`.

**Подход Б - роль лежит в JWT**, куда её кладёт Custom Access Token
Hook Supabase (функция, которую GoTrue вызывает при выпуске токена).
Политика читает роль прямо из `auth.jwt()`, без единого подзапроса.
Цена - обратная: смена роли применяется только после перевыпуска
токена, то есть с задержкой до следующего логина или истечения
текущего access token'а. Понижение прав срабатывает не сразу - для
точки проката, где деактивация сотрудника должна блокировать доступ
немедленно (уволенный оператор не должен продолжать выдавать инструмент
до истечения своего токена), это неприемлемый компромисс.

Проект реализует подход А. Подход Б остаётся как альтернатива, которую
стоило бы рассмотреть там, где мгновенное отключение доступа не
критично, а частота чтения роли высока настолько, что подзапрос
становится узким местом.

### `current_staff_role()`: `security definer` против рекурсии

Прямой подзапрос `select role from staff where user_id = auth.uid()`
внутри политики *на саму* `staff` создаёт рекурсию: чтобы решить, видна
ли строка `staff`, Postgres должен применить политику `staff`, которая
сама читает `staff`, - бесконечный цикл, обрывающийся ошибкой `42P17`.
Для политик на *других* таблицах (`tools`) проблемы рекурсии нет, но
вынести чтение роли в отдельную функцию всё равно правильно - она нужна
многим политикам сразу, и логика "кто сейчас действует" должна быть
в одном месте.

```sql
create function public.current_staff_role()
returns public.staff_role
language sql
stable
security definer
set search_path = ''
as $$
select s.role
from public.staff s
where s.user_id = auth.uid()
  and s.is_active
$$;
```

`security definer` - функция выполняется с правами того, кто её
*создал* (владелец функции, обычно `postgres`), а не того, кто её
*вызывает*. Владелец таблицы `staff` - тот же `postgres`, а RLS к
владельцу таблицы не применяется (если явно не включён `FORCE ROW LEVEL
SECURITY`, что здесь не сделано). Поэтому чтение `staff` внутри функции
идёт мимо политик `staff`, и рекурсии не возникает.

Это не дыра в безопасности, потому что функция не отдаёт наружу
содержимое `staff` - она отдаёт ровно одно значение: роль строки,
принадлежащей самому вызывающему (`where s.user_id = auth.uid()`).
Чужая роль так узнать не получится, сколько ни вызывай эту функцию.

`stable` - объявление, что в пределах одного запроса функция без
побочных эффектов и её результат не меняется. Это *разрешает*
планировщику Postgres вызвать функцию один раз на запрос вместо одного
раза на строку, но не *обязывает* - решение остаётся за планировщиком.
Гарантию "ровно один раз" даёт другой приём, разобранный ниже.

`set search_path = ''` - `security definer`-функция без явно
зафиксированного пути поиска уязвима: если в схеме, которая окажется в
пути поиска раньше `public`, кто-то создаст объект с именем `staff`,
функция прочитает его с правами `postgres`. Пустой путь заставляет
писать только полные имена (`public.staff`, `auth.uid()`), и подмена
через объект-двойник в другой схеме становится невозможной.

`revoke execute ... from public` затем `grant execute ... to
authenticated` - Postgres по умолчанию выдаёт `execute` на новую функцию
роли `PUBLIC` (то есть всем, включая `anon`). `anon` вызывать эту
функцию незачем, `authenticated` - нужно, потому что её вызывают
политики от имени вызывающего пользователя.

### `stable` и `(select ...)` как InitPlan

`stable` само по себе не гарантирует однократный вызов на запрос - это
свойство влияет на то, что планировщик *имеет право* сделать, а не на
то, что он *обязан*. Гарантию даёт обёртка вызова в `select` внутри
политики:

```sql
using ((select public.current_staff_role()) = 'SUPERADMIN')
```

вместо

```sql
using (public.current_staff_role() = 'SUPERADMIN')
```

`(select ...)` превращает вызов в отдельный подзапрос, который
планировщик Postgres умеет вычислить как InitPlan - однократно, до
перебора строк, и подставить готовое значение в условие для каждой из
них. Без обёртки `stable`-функция технически *может* быть вычислена
планировщиком так же, но в общем случае это не гарантировано (особенно
если функция участвует в более сложном выражении или план запроса
меняется), и в PostgREST-запросах, где план строится заново на каждый
HTTP-запрос, разница между "вызвано один раз" и "вызвано на каждую
строку" - это разница между одним обращением к `staff` и N обращениями
при выборке N строк. Все политики проекта, вызывающие
`current_staff_role()`, оборачивают вызов в `(select ...)` без
исключений.

### `USING` против `WITH CHECK`

`USING` фильтрует *существующие* строки: для `SELECT` - какие строки
видны, для `UPDATE`/`DELETE` - какие строки вообще можно тронуть,
проверяется по их состоянию *до* изменения. `WITH CHECK` проверяет
*записываемую* строку - ту, что получится после `INSERT` или `UPDATE`,
уже с новыми значениями. Для `INSERT` есть только `WITH CHECK` -
старой строки не существует, проверять нечего.

Разница видна на политике UPDATE для `staff`, где суперадмин не может
понизить или деактивировать сам себя:

```sql
create policy "staff: superadmin updates"
on public.staff for update
to authenticated
using ((select public.current_staff_role()) = 'SUPERADMIN')
with check (
  (select public.current_staff_role()) = 'SUPERADMIN'
  and (
    user_id <> (select auth.uid())
    or (role = 'SUPERADMIN' and is_active)
  )
);
```

`USING` пропускает суперадмина к любой строке, включая собственную -
он должен иметь возможность её *найти* запросом. `WITH CHECK`
дополнительно требует: либо строка не его собственная, либо после
записи она всё ещё `role = 'SUPERADMIN' and is_active`. Суперадмин
может обновить свою строку (поменять `full_name`, например), но не
может записать в неё понижающую роль или `is_active = false` - его
собственная строка проходит `USING` (она видна), но не проходит `WITH
CHECK` (новая версия нарушает условие). Без разделения `USING`/`WITH
CHECK` на два условия эту защиту от самоблокировки было бы невозможно
выразить: единое условие либо пускало бы к своей строке всегда, либо
не пускало бы никогда.

Там, где право менять строку зависит только от роли, а не от того, что
именно меняется (`tools`), `USING` и `WITH CHECK` совпадают дословно:

```sql
create policy "tools: manager+ updates"
on public.tools for update
to authenticated
using ((select public.current_staff_role()) >= 'MANAGER')
with check ((select public.current_staff_role()) >= 'MANAGER');
```

Без явного `WITH CHECK` Postgres в этом случае применил бы `USING` и к
новой версии строки автоматически - поведение было бы тем же, но явная
запись читается без знания этого правила по умолчанию, поэтому в
проекте `WITH CHECK` дублируется, даже когда формально можно было бы
опустить.

### Три исхода политики

Обращение к таблице с RLS даёт один из трёх результатов, и от чего
зависит каждый - твёрдое знание, без которого читать любую политику
в этом проекте сложнее:

1. **Пусто, без ошибки** - грант есть, но ни одна политика (или
   единственная политика с `USING`) не пропускает: `SELECT` вернёт
   `[]`/`200`, `UPDATE`/`DELETE` заявят `0` затронутых строк.
2. **`0` строк, без ошибки** - частный случай предыдущего для
   `UPDATE`/`DELETE`: запрос выполнился, но `USING` не нашёл ни одной
   строки, которую вызывающему разрешено менять. Пример - `OPERATOR`
   пытается `update staff set role = 'SUPERADMIN' where user_id =
   auth.uid()`: `USING` политики `"staff: superadmin updates"`
   отсекает его строку раньше, чем дело дойдёт до `WITH CHECK`, - ошибки
   нет, просто ничего не изменилось.
3. **`42501`** - либо нет гранта на операцию вообще (первый слой,
   до всяких политик), либо есть подходящий `USING`, но результат не
   проходит `WITH CHECK` при `INSERT`/`UPDATE`. Пример - тот же
   `SUPERADMIN` пытается `update staff set role = 'MANAGER' where
   user_id = auth.uid()`: `USING` пропускает (его собственная строка
   видна), а `WITH CHECK` отклоняет новую версию - в отличие от исхода
   2, здесь Postgres нашёл строку для изменения, но записать её не
   разрешил, и это уже ошибка, а не тихий `0`.

### Как тест имитирует пользователя

`tests/policies/02_roles.sql` не делает ни одного HTTP-запроса - вместо
этого он воспроизводит внутри обычной SQL-сессии ровно то, что
PostgREST делает при получении запроса с access token'ом:

```sql
create function pg_temp.act_as(p_email text) returns void
language plpgsql as $$
declare v_uid uuid;
begin
  reset role;
  select id into strict v_uid from auth.users where email = p_email;
  perform set_config('request.jwt.claims',
    json_build_object('sub', v_uid, 'role', 'authenticated')::text, true);
  set local role authenticated;
end $$;
```

`request.jwt.claims` - GUC-переменная (настройка сессии Postgres), из
которой `auth.uid()` на самом деле читает `sub` (id пользователя):
PostgREST перед выполнением запроса кладёт туда распарсенные claims
JWT-токена именно в этот параметр, и `auth.uid()` - это просто обёртка
над `current_setting('request.jwt.claims', true)::json->>'sub'`. `set
local role authenticated` переключает Postgres-роль текущей
транзакции - тоже то, что делает PostgREST, выбирая роль по `role` из
токена. Вместе эти две строки дают Postgres-сессию, неотличимую для
политик от настоящего запроса пользователя с этим `sub`, - RLS
проверяет `auth.uid()` и `current_setting`, а не откуда взялось само
соединение.

Всё внутри `begin; ... rollback;`, так что фикстуры и любые изменения,
сделанные тестируемыми ролями, исчезают вместе с транзакцией.
Вспомогательные функции лежат в `pg_temp` - временной схеме,
привязанной к сессии, - и пропадают вместе с ней же, не оставляя следов
в `public`.

## 3. Порядок чтения файлов

1. **`supabase/migrations/20260918094510_staff_and_roles.sql`**, по
   секциям в порядке файла:
   - **Секция 1, тип `staff_role`.** `enum`, а не `text + check`:
     Postgres сравнивает значения `enum` по порядку объявления
     (`OPERATOR < MANAGER < SUPERADMIN`), это и даёт политикам писать
     `role >= 'MANAGER'` вместо перечисления конкретных ролей. Добавить
     промежуточную роль позже можно через `ALTER TYPE ... ADD VALUE ...
     BEFORE` без правки существующих политик; убрать значение из `enum`
     нельзя иначе как пересозданием типа - это уже цена подхода, а не
     недостаток комментария.
   - **Секция 2, таблица `staff`.** `user_id` - одновременно первичный
     и внешний ключ: у пользователя Auth не может быть больше одной
     строки сотрудника. `on delete restrict`, а не `cascade`: сотрудника
     не удаляют из `auth.users`, а деактивируют (`is_active = false`) -
     на `staff` в будущих этапах сошлются аренды и аудит, и `cascade`
     молча стёр бы, кто оформлял выдачу. Дефолт роли - `OPERATOR`,
     минимальная: забытое явное значение не должно давать лишних прав.
   - **Секция 3, функция и гранты на неё.** Разобрана целиком в разделе 2
     выше.
   - **Секция 4, гранты и политики `staff`.** Порядок политик SELECT
     важен для понимания, но не для работы: `"staff: read own row"` и
     `"staff: superadmin reads all"` - это две отдельные политики на
     один и тот же `for select`, и они объединяются через `OR`, а не
     заменяют друг друга. Обычный сотрудник видит свою строку по первой,
     суперадмин - все строки по второй (и тоже свою по первой; итог тот
     же набор строк).
   - **Секция 5, `tools`: матрица прав.** `drop policy if exists
     "authenticated can read tools"` убирает временную политику этапа 1
     (`using (true)`, пускавшую любого залогиненного вне зависимости от
     наличия строки в `staff`) и заменяет её политикой, завязанной на
     `current_staff_role()`.
2. **`supabase/migrations/20260918155352_grants_service_role.sql`** и
   **`20260918162404_grant_service_role_select_staff.sql`** - история
   про грант `service_role`, разобрана в разделе "Грабли" ниже как
   пример того, когда исправление идёт новой миграцией, а не правкой
   уже применённой.
3. **`tests/policies/02_roles.sql`** - структура файла: вспомогательные
   `pg_temp`-функции (`act_as`, `act_as_anon`, `expect_error`,
   `expect_count`, `expect_affected`) в начале, затем сценарии по ролям
   по возрастанию прав (`OPERATOR` → `MANAGER` → `SUPERADMIN`), в конце -
   проверка, что деактивация действует немедленно (без перелогина) и что
   `anon` отсекается на первом слое. Каждая строка сценария - это одна
   строка матрицы прав из `docs/roles.md`, выраженная запросом.
4. **`docs/roles.md`** - та же матрица в табличном виде, для сверки.
5. **`src/features/staff/queries.ts`** - как роль текущего пользователя
   попадает в интерфейс: `supabase.rpc('current_staff_role')` вызывает
   ровно ту функцию из секции 3 миграции, с правами вызывающего (grant
   `execute` выдан `authenticated` не просто для политик, а и для этого
   вызова тоже). `hasRole()` - сравнение только для показа/скрытия
   элементов интерфейса; в комментарии над ней явно указано, что защита
   - в политиках, не здесь (используется начиная с интерфейса главы 03,
   но сама функция - часть механики этой главы).

## 4. Решения и альтернативы

**Роль в таблице, а не в JWT.** Разобрано в разделе 2 как основной
материал главы. Главный довод - мгновенная деактивация; альтернатива
(Custom Access Token Hook) осталась нереализованной, но уместна там, где
задержка обновления роли на один логин не критична, а нагрузка от
подзапроса `staff` заметна.

**`enum` для роли и категории, а не `text + check`.** Уже разобрано в
разделе 3 (секция 1 миграции) - иерархия ролей выражается порядком
объявления, что делает возможным `>=` в политиках вместо списка ролей.

**`staff.user_id` как первичный ключ, без отдельного `id`.** Строка
сотрудника имеет смысл только вместе с конкретным пользователем Auth, и
одному пользователю не может соответствовать больше одной роли -
отдельный суррогатный `id` не добавил бы никакой сущности, которую
нельзя было бы идентифицировать через `user_id`, а лишь потребовал бы
дополнительного уникального ограничения на этот же `user_id`.

**Защита от самоблокировки в политике, а не в приложении.** Альтернатива
- проверять в UI, что суперадмин не редактирует сам себя, и полагаться
на это. Отклонено по общему принципу проекта: проверка в коде - для
удобства интерфейса, а не для защиты (`CLAUDE.md`), прямой запрос к
API в обход интерфейса иначе позволил бы последнему суперадмину
заблокировать систему одним запросом.

## 5. Как повторить с нуля

```bash
npm run db:new staff_and_roles
# вписать SQL: тип staff_role, таблица staff, current_staff_role(),
# гранты и политики staff, замена политики tools

npm run db:push
npm run seed:staff       # создаёт трёх тестовых сотрудников через Admin API
npm run db:types

set -a; source .env.local; set +a
psql "$DB_URL" -v ON_ERROR_STOP=1 -f tests/policies/02_roles.sql
```

Если в процессе вскрывается недостающий грант (как это произошло с
`service_role` на `staff`, раздел "Грабли") - отдельная миграция с этим
грантом, `db:push` снова, тест снова.

## 6. Как проверить

```bash
set -a; source .env.local; set +a
psql "$DB_URL" -v ON_ERROR_STOP=1 -f tests/policies/02_roles.sql
```

Ожидаемый вывод - последовательность `NOTICE:  ok [...] ...` для каждой
проверки сценария и `ROLLBACK` в самом конце без единого `FAIL`. Первый
же `FAIL` останавливает скрипт (`ON_ERROR_STOP=1`) с текстом, в какой
именно проверке разошлись ожидание и факт.

Ручная проверка: три раза войти в интерфейс под `operator@example.com`,
`manager@example.com`, `admin@example.com` (пароль - `SEED_PASSWORD` из
`.env.local`) и убедиться, что кнопки создания/удаления инструмента
показываются или скрываются согласно `docs/roles.md` - это проверка UX,
не защиты; защиту уже подтвердил SQL-тест выше.

## 7. Грабли

**Прямой подзапрос к `staff` внутри политики `staff` даёт `42P17`
(рекурсия).** Возникает, если попытаться выразить `"staff: superadmin
reads all"` без функции, через `using (exists (select 1 from staff s2
where s2.user_id = auth.uid() and s2.role = 'SUPERADMIN'))` - подзапрос
к `staff` снова включает RLS `staff`, которая опять делает подзапрос, и
так по кругу. Чинится выносом чтения роли в `security definer`-функцию
(раздел 2).

**Пропущенный грант для `service_role` на `staff`.** Реальная история
проекта: `20260918155352_grants_service_role.sql` выдал `service_role`
`insert, update` на `staff`, рассчитывая, что upsert-скрипт
(`scripts/seed-staff.ts`, `on conflict (user_id) do update`) больше
ничего не требует. Прогон `npm run seed:staff` вскрыл `42501` с
подсказкой `GRANT SELECT ON public.staff`: `ON CONFLICT DO UPDATE`
читает существующую строку по `user_id` и значения `excluded`, и для
этого Postgres требует `SELECT` на таблицу - либо это делает сам PostgREST,
оборачивающий запись в CTE, который читает из неё уже без `.select()`
в клиенте. Исправлено отдельной миграцией
(`20260918162404_grant_service_role_select_staff.sql`), а не правкой
уже отправленной: та миграция уже прошла через `db:push`, и повторно
CLI её не выполнит (глава 00, раздел "История применённых миграций").
Важная тонкость: сам недостающий грант идемпотентен (`grant` можно
выполнить повторно без вреда), и в принципе можно было бы поправить
первый файл и вернуть его через `migration repair --status reverted` +
`db:push` - но так делают, когда правят *содержимое* уже применённого
идемпотентного файла, а не когда *добавляют* новый грант, которого в
файле изначально не было. Здесь это именно добавление, поэтому выбор -
новая миграция, без вопроса об идемпотентности.

**Ожидание, что `stable` сама по себе гарантирует один вызов функции на
запрос.** `stable` разрешает кешировать результат в пределах запроса, но
не обязывает. Без `(select public.current_staff_role())` вызов может
(не обязан, но может) выполняться на каждую строку - для больших выборок
это N обращений к `staff` вместо одного. Каждая политика проекта,
вызывающая эту функцию, оборачивает вызов в `select`.

**Опечатка в сравнении ролей после добавления новой роли `enum`'ом не
на своём месте.** `ALTER TYPE public.staff_role ADD VALUE 'X' BEFORE
'MANAGER'` меняет порядок сравнения молча - все политики с `>=`
пересчитывают иерархию автоматически, но если роль по ошибке добавлена
`AFTER` вместо `BEFORE`, существующие политики продолжат работать
синтаксически правильно, просто с неверной иерархией прав, - это не
даст ошибки, только неверный результат, и заметно только тестом на
конкретную новую роль.

## 8. Вопросы для самопроверки

<details>
<summary>Почему роль пользователя читается через функцию <code>current_staff_role()</code>, а не прямым подзапросом к <code>staff</code> внутри политики на <code>staff</code>?</summary>

Прямой подзапрос к <code>staff</code> внутри политики на саму
<code>staff</code> заново включает RLS этой же таблицы, которая снова
делает подзапрос - бесконечная рекурсия, ошибка <code>42P17</code>.
</details>

<details>
<summary>Что даёт <code>security definer</code> в этой функции и почему это не дыра в безопасности?</summary>

Функция выполняется с правами владельца (<code>postgres</code>), который
владеет и таблицей <code>staff</code>, - RLS к владельцу таблицы не
применяется, поэтому чтение внутри функции идёт мимо политик и рекурсии
нет. Дыры нет, потому что функция фильтрует по
<code>auth.uid()</code> вызывающего и отдаёт только его собственную
роль - чужие данные наружу не идут ни при каком вызове.
</details>

<details>
<summary>Зачем оборачивать вызов <code>current_staff_role()</code> в <code>(select ...)</code> внутри политики, если функция уже помечена <code>stable</code>?</summary>

<code>stable</code> только разрешает планировщику вычислить функцию один
раз на запрос, но не обязывает. Обёртка в <code>select</code> превращает
вызов в InitPlan, который гарантированно вычисляется один раз, до
перебора строк, а не потенциально на каждую строку.
</details>

<details>
<summary>В чём разница между <code>USING</code> и <code>WITH CHECK</code>?</summary>

<code>USING</code> проверяет существующую строку - какие строки видны
или доступны для изменения по их состоянию <em>до</em> записи.
<code>WITH CHECK</code> проверяет строку, которая получится <em>после</em>
записи. Для <code>INSERT</code> есть только <code>WITH CHECK</code> -
старой строки не существует.
</details>

<details>
<summary>Какие три исхода возможны при обращении к таблице с RLS и от чего зависит каждый?</summary>

Пусто/<code>0</code> строк без ошибки - грант есть, но <code>USING</code>
ни одной строки не пропускает. <code>42501</code> - либо гранта нет
вообще (до политик дело не доходит), либо строка для
<code>INSERT</code>/<code>UPDATE</code> не проходит <code>WITH CHECK</code>.
Успех - оба слоя пройдены.
</details>

<details>
<summary>Как SQL-тест имитирует запрос от конкретного пользователя без реального HTTP-запроса?</summary>

Кладёт в GUC-переменную <code>request.jwt.claims</code> JSON с
<code>sub</code> (id пользователя) - тем же, что читает
<code>auth.uid()</code>, - и переключает Postgres-роль сессии
(<code>set local role authenticated</code>). Это ровно то, что делает
PostgREST на каждый настоящий запрос: политики не отличают эту
симуляцию от реального обращения.
</details>

<details>
<summary>Почему роль хранится в таблице <code>staff</code>, а не в JWT через Custom Access Token Hook - и какой ценой?</summary>

Роль в таблице позволяет отозвать доступ мгновенно (деактивация
действует со следующего запроса, без перелогина) - для точки проката
это важнее. Цена - каждый запрос к защищённой таблице тянет за собой
дополнительное чтение <code>staff</code> (через функцию). Роль в JWT
убрала бы этот подзапрос, но понижение прав применялось бы только после
перевыпуска токена.
</details>

<details>
<summary>Почему грант <code>SELECT</code> для <code>service_role</code> на <code>staff</code> добавлен отдельной миграцией, а не правкой уже применённой?</summary>

Миграция с первым грантом уже была отправлена через <code>db:push</code>,
и CLI не переприменит уже отмеченную в истории версию без явного
<code>migration repair</code>. Здесь это добавление нового гранта, а не
правка содержимого существующего идемпотентного файла, поэтому выбор -
новая миграция.
</details>
