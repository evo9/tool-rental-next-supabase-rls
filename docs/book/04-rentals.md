# Глава 04. Аренда: выдача и возврат

## 1. Задача этапа

Оператор выдаёт клиенту сразу несколько физических единиц инструмента,
фотографирует каждую в момент выдачи, а потом принимает возврат - целиком
или по частям, тоже с фото каждой единицы. Требование этапа не про
интерфейс, а про то, что база обязана гарантировать сама, не полагаясь
на аккуратность кода: одна единица не может одновременно оказаться в
двух активных арендах, а статус единицы (`AVAILABLE`/`RENTED`/...)
обязан совпадать с тем, что на самом деле записано в аренде, а не быть
отдельным полем, которое кто-то забыл обновить.

Здесь впервые в проекте одно действие пользователя - выдача - требует
нескольких согласованных вставок в разные таблицы. До этого этапа
любая операция была одной строкой в одной таблице; выдача аренды -
это аренда плюс N позиций, которые должны появиться вместе или не
появиться вовсе. Отсюда - RPC, транзакции и триггеры, которые пишут
за пользователя в таблицы, где у него самого нет прав на запись.

## 2. Новая механика

### Частичный уникальный индекс

Обычный `unique index` запрещает повтор значения во всей таблице.
**Частичный** уникальный индекс добавляет `WHERE` и запрещает повтор
только среди строк, которые этому условию удовлетворяют - остальные
строки для него как будто не существуют.

```sql
create unique index rental_items_active_unit
  on public.rental_items (tool_unit_id)
  where returned_at is null;
```

У одной единицы инструмента за время её жизни могут быть десятки строк
в `rental_items` - по одной на каждую аренду, в которой она когда-либо
участвовала. Обычный `unique (tool_unit_id)` запретил бы это в принципе:
единицу нельзя было бы сдать в аренду второй раз никогда. Частичный
индекс смотрит только на строки с `returned_at is null` - "активные"
позиции, - и держит инвариант "не больше одной активной позиции на
единицу", не трогая историю уже закрытых.

Это надёжнее проверки в коде ("сначала SELECT, убедиться, что единица
свободна, потом INSERT") при параллельных запросах: между `SELECT` и
`INSERT` всегда есть окно, в которое может влезть вторая транзакция и
тоже увидеть единицу свободной. Уникальный индекс проверяется самим
Postgres в момент записи, окна для гонки не остаётся - см. следующий
подраздел.

### Что происходит при двух параллельных вставках в уникальный индекс

Открыть два сеанса `psql` к одной облачной базе и в каждом начать
транзакцию:

```sql
-- сессия 1
begin;
insert into public.rental_items (rental_id, tool_unit_id)
values ('<rental-1>', '<та же единица>');
-- не коммитить, оставить открытой

-- сессия 2 (параллельно, тот же tool_unit_id)
begin;
insert into public.rental_items (rental_id, tool_unit_id)
values ('<rental-2>', '<та же единица>');
-- сессия 2 здесь не отвечает - висит
```

Вторая вставка не падает с ошибкой сразу и не проходит - она **ждёт**.
Postgres, вставляя строку в таблицу с уникальным индексом, должен
убедиться, что конфликтующей строки не существует, а вторая транзакция
как раз могла её создать (просто ещё не зафиксировала). Единственный
безопасный вариант для Postgres - подождать, чем закончится первая
транзакция. Если сессия 1 делает `commit`, сессия 2 сразу же
разблокируется и получает `23505 duplicate key value violates unique
constraint "rental_items_active_unit"` - индекс теперь точно видит
конфликт. Если бы сессия 1 сделала `rollback`, сессия 2 прошла бы
успешно - конфликтующей строки в итоге не оказалось.

Это ровно то же самое ожидание, которое каждый день происходит внутри
`issue_rental()`, просто здесь оно сделано явным на двух отдельных
подключениях, чтобы увидеть его глазами, а не поверить на слово.

### Инвариант через данные, а не через флаг

`tool_units.status` не может значить что попало - `RENTED` обязано
означать "у единицы есть активная позиция в `rental_items`", а не
"кто-то в какой-то момент выставил этот статус". Один из способов
разрешить триггеру `tool_units_guard_status` отличать "легитимное"
изменение статуса (то, что делает `rental_items_sync_unit`) от ручного -
завести флаг сессии:

```sql
-- Так делать не надо - демонстрация неправильного подхода.
if current_setting('app.from_trigger', true) is distinct from 'yes' then
  raise exception '...';
end if;
```

Этот флаг живёт в GUC (session-local настройка Postgres) текущего
подключения. Проблема в том, что GUC для клиента ничем не защищён:
любой `authenticated` пользователь, отправляющий обычный запрос через
PostgREST, при желании мог бы сам выполнить `select set_config('app.from_trigger',
'yes', true)` перед своим запросом (или это подстроил бы вредоносный
клиент API) - и правило перестало бы что-либо проверять.

Вместо этого `tool_units_guard_status` смотрит на **данные**:

```sql
select exists (
  select 1 from public.rental_items ri
  where ri.tool_unit_id = old.id and ri.returned_at is null
) into v_has_active_position;
```

Подделать эту проверку нечем: чтобы она увидела "активную позицию", в
`rental_items` действительно должна лежать строка с `returned_at is
null` - а вставка и изменение `rental_items` защищены собственными
грантами, политиками и триггерами (в частности, тем самым частичным
индексом, который не даст завести вторую активную позицию произвольно).
Подделать факт в данных настолько же сложно, насколько сложно обойти
всю остальную защиту проекта, - а подделать флаг сессии можно одной
строкой.

### Триггер, который принудительно ставит время

`rental_items.returned_at` грантован клиенту на запись - оператору
нужно самому отметить момент приёмки возврата. Но именно поэтому
значению, которое прислал клиент, нельзя верить буквально: ничто не
мешает отправить `returned_at` в прошлом и задним числом убрать
клиенту просрочку.

```sql
create function public.rental_items_set_return()
    returns trigger
    language plpgsql
    security invoker
    set search_path = ''
as $$
begin
  if old.returned_at is not null then
    raise exception 'return is already recorded and cannot be changed'
      using errcode = 'P0001';
  end if;
  if new.returned_at is null then
    raise exception 'return date cannot be cleared'
      using errcode = 'P0001';
  end if;

  new.returned_at := now();
  new.returned_by := auth.uid();
  return new;
end;
$$;
```

Приложение обязано прислать в `returned_at` что-нибудь не-`null` (это
проверяет вторая часть триггера и что без этого возврат вообще не
запустится), но конкретное значение, которое клиент туда положил, в
строку не попадает - `before`-триггер подменяет его на `now()` уже
внутри базы, до того как строка будет записана. То же с `returned_by` -
клиент это поле в принципе не грантован писать, но если бы был, триггер
всё равно подставил бы `auth.uid()` поверх.

### `security definer` в триггерной функции, которая пишет в чужие таблицы

Когда оператор вставляет строку в `rental_items`, у него для этого есть
собственные права - грант на `insert (rental_id, tool_unit_id)` и
политика, разрешающая это для любого активного сотрудника. Но сама
выдача должна ещё и перевести единицу в `RENTED` (грант на `status` есть
только у `MANAGER+`) и, при закрытии последней позиции, поставить
`rentals.status = 'CLOSED'` (эта колонка вообще не грантована клиенту).
Оператору для этого не хватает прав - и не должно хватать, у него нет
причин напрямую писать в `tool_units`/`rentals`.

```sql
create function public.rental_items_sync_unit()
    returns trigger
    language plpgsql
    security definer
    set search_path = ''
as $$
begin
  -- ... читает rental_items, пишет в tool_units и rentals
end;
$$;
```

`security definer` выполняет тело функции с правами того, кто её создал
(`postgres`), а не того, кто вызвал триггер (оператор). Это не расширяет
права оператора в общем смысле - функция не принимает от него ничего,
кроме факта, что он вставил или обновил строку `rental_items`, которую
и так разрешено вставлять/обновлять его собственным грантам и политикам.
Всё, что функция читает и пишет дальше, она берёт из данных уже
вставленной строки (`new.tool_unit_id`, `new.rental_id`), а не из
произвольного ввода, - оператор не может через эту функцию попросить
изменить статус чужой, не связанной с его действием единицы.

Это тот же приём, что `current_staff_role()` в главе 02, только там
`security definer` даёт функции право *прочитать* защищённую таблицу
в обход рекурсии, а здесь - право *записать* в таблицы, до которых у
вызывающего изначально нет прав дотянуться напрямую.

### Порядок срабатывания нескольких before-триггеров на одной таблице

Общее правило Postgres: если на одну таблицу для одного и того же
события (`insert`, `update` конкретных колонок) навешано несколько
`before`-триггеров, они выполняются по очереди в алфавитном порядке
**имён триггеров**, а не порядке объявления в файле миграции.
Иллюстрация (не код этого проекта, просто чтобы увидеть эффект):

```sql
create trigger b_first before insert on t for each row execute function f1();
create trigger a_second before insert on t for each row execute function f2();
-- при insert сработает a_second, затем b_first - по алфавиту, не по
-- порядку create trigger
```

Если один из триггеров меняет `NEW`, а другой читает уже изменённое
значение, порядок становится частью корректности - и тогда правило
стоит явно упомянуть в комментарии над триггером (стандарт проекта,
раздел "Триггер" в `CLAUDE.md`).

В этой миграции такого расклада нет ни на одной таблице: у `tool_units`
один `before`-триггер на `update of status`, у `rentals` один `before`
на `insert`, у `rental_items` один `before` на `update of returned_at`.
Каждый инвариант держит ровно один триггер, а не несколько
взаимодействующих между собой, - это сознательный выбор (раздел 4), и
правило про алфавитный порядок здесь предупреждает будущее, а не
описывает то, что уже произошло: как только на одну из этих таблиц (или
на `rentals`/`rental_items` этапа 6, когда там появится аудит-триггер)
добавят второй `before`-триггер на то же событие, их относительный
порядок нужно будет продумать и задокументировать явно.

### RPC: атомарность без расширения прав

RPC в терминах Supabase - обычная SQL/PL/pgSQL-функция в схеме
`public`, которую PostgREST отдаёт наружу отдельным HTTP-путём:
`POST /rest/v1/rpc/<имя функции>`. Со стороны клиента это `supabase.rpc('issue_rental',
{ ... })` - не отличается от вызова обычного запроса, только вместо
`from('table')` указывается имя функции, а тело запроса становится её
аргументами.

```sql
create function public.issue_rental(
    p_customer_id uuid,
    p_planned_return_at timestamptz,
    p_unit_ids uuid[]
) returns table (rental_id uuid, rental_item_id uuid, tool_unit_id uuid)
    language plpgsql
    security invoker
as $$ ... $$;
```

Зачем здесь RPC, а не серия отдельных запросов из приложения: выдача -
это аренда плюс N позиций, и всё это должно появиться в базе вместе или
не появиться вовсе. Несколько отдельных HTTP-запросов от клиента такой
гарантии не дают - сеть может оборваться между вставкой аренды и частью
позиций, и в базе останется аренда без части единиц. Вызов RPC - это
один SQL-вызов, а значит одна транзакция Postgres целиком: если внутри
функции что-то упало (недоступная единица, дубль в массиве), откатывается
вообще всё, что она успела сделать, включая уже вставленную строку
`rentals`.

Важно, что это исключительно про атомарность, не про права: функция
объявлена `security invoker` - она выполняется с правами того, кто её
вызвал, и каждая вставка внутри нее проходит те же гранты и политики,
что прошла бы, приди она отдельным запросом через PostgREST напрямую.
Прямой `INSERT` в `rentals` и `rental_items`, минуя эту функцию,
подчиняется тем же правилам и даёт тот же результат - RPC не место,
где живут правила, только место, где несколько вставок становятся
одной транзакцией.

## 4. Решения и альтернативы

**Позиция вставляется в открытую аренду политикой, а не триггером.**
Правило "нельзя добавить позицию в `CLOSED` аренду" можно было бы
держать `before insert`-триггером на `rental_items`, читающим статус
родительской аренды, - симметрично `rentals_guard_customer`. Выбрана
политика:

```sql
create policy "staff can add items to active rentals"
on public.rental_items for insert
to authenticated
with check (
  (select public.current_staff_role()) is not null
  and exists (
    select 1 from public.rentals r
    where r.id = rental_id and r.status = 'ACTIVE'
  )
);
```

Причина - у `INSERT` нет `OLD`, а значит нет ничего, ради чего в этом
конкретном случае нужен именно триггер (в отличие от `customers_guard_category`
в главе 03, где правило зависело от сравнения старого и нового значения).
Всё необходимое - аренда существует и она `ACTIVE` - выражается одним
подзапросом в `WITH CHECK`, без отдельной функции и `create trigger`.
Цена решения симметрична: если правило когда-нибудь станет сложнее
одного условия (например, потребуется разное поведение для разных
причин, почему аренда закрыта), триггер с явным текстом ошибки будет
читаться понятнее одной длинной политики.

**`tool_units_guard_status` - один триггер на три правила, а не три
триггера.** WRITTEN_OFF как терминальный статус, переход в RENTED и
выход из RENTED - три отдельных проверки, но все они об одном и том же
инварианте (статус согласован с данными `rental_items`) и все смотрят
на одну и ту же связку `OLD`/`NEW`/`exists`. Разнесение по трём
триггерам добавило бы вопрос про их взаимный порядок (раздел 2 выше) без
всякой пользы - единый триггер проще читать и проще убедиться, что
инвариант держится целиком, а не по частям.

**Гранты `service_role` на `tool_units` и `tools` добавлены сразу, а не
после первой ошибки.** В главе 02 такой же грант на `staff` появился
только после того, как `npm run seed:staff` реально упал с `42501` -
там это было честной находкой по ходу разработки. Здесь тот же урок уже
известен заранее (сид этого этапа тоже пойдёт через `service_role` и
`upsert`), поэтому грант добавлен в первой же миграции, а не оставлен на
обнаружение.

**`returns table (...)` у `issue_rental`, а не просто `rental_id
uuid`.** Задание описывает именно такую сигнатуру - функция отдаёт по
одной строке на каждую вставленную позицию (`rental_item_id`,
`tool_unit_id`), а не только общий `rental_id`. Это даёт клиенту сразу
все идентификаторы, нужные для следующего шага (загрузка фото по
каждой позиции), без отдельного запроса `select * from rental_items
where rental_id = ...` сразу после вызова.

## 6. Как проверить

```bash
set -a; source .env.local; set +a
psql "$DB_URL" -v ON_ERROR_STOP=1 -f tests/policies/02_roles.sql
psql "$DB_URL" -v ON_ERROR_STOP=1 -f tests/policies/03_customers.sql
psql "$DB_URL" -v ON_ERROR_STOP=1 -f tests/policies/04_rentals.sql
```

Ожидание - то же, что в предыдущих главах: последовательность `NOTICE:
ok [...] ...`, без единого `FAIL`, до `ROLLBACK`. Первые два файла
проверяют, что этап 4 не сломал уже работавшие политики (регрессия) -
их обязательно гонять вместе с новым, не только новый отдельно.

Идемпотентность сида - отдельная проверка, не заменяющая SQL-тесты:

```bash
npm run seed:staff
npm run seed:staff   # второй раз подряд, без ошибок
```

Руками, что не покрыто автоматическими тестами:

- **Блокировка на уникальном индексе.** Два сеанса `psql` к одной базе:
  в обоих `begin`, в обоих `insert into rental_items (...)` с одним и
  тем же `tool_unit_id`. Второй сеанс не отвечает, пока первый не
  сделает `commit` (тогда `23505`) или `rollback` (тогда проходит).
  Понять, почему именно ждёт, а не падает сразу, - раздел 2.
- **Прочитать `rental_items_sync_unit`** и объяснить своими словами,
  почему `security definer`, какие именно права это даёт и почему это
  не дыра (раздел 2, подраздел про `security definer`).
- **Прочитать `tool_units_guard_status`** и объяснить, почему проверка
  идёт по данным `rental_items`, а не по флагу сессии (раздел 2).
- **Выдача прямым `INSERT`, без RPC.** Через `curl` с access token
  сотрудника: `insert into rentals (customer_id, planned_return_at)`,
  затем `insert into rental_items (rental_id, tool_unit_id)` для той же
  единицы, что уже выдана в другой аренде, - ожидание `23505`, то же
  самое, что даёт `issue_rental()`. Правила не обходятся в обход RPC.
- **`returned_at` задним числом через `curl`** - `update rental_items
  set returned_at = '2000-01-01', return_photo_path = '<путь>' where id
  = ...` - в ответе `returned_at` окажется текущим временем, не тем,
  что отправили.

## 7. Грабли

**`before update of status` срабатывает от наличия колонки в `SET`, а
не от изменения значения - на этом упал сид.** `npm run seed:staff`
делает `upsert` по `tool_units.inventory_number` с `onConflict`, и
Postgres формирует `ON CONFLICT DO UPDATE` со всеми колонками payload,
включая `status`, даже когда значение то же самое. Первая версия
`tool_units_guard_status` не проверяла, действительно ли статус
меняется:

```sql
-- было (неверно): срабатывает и когда new.status = old.status
if old.status = 'WRITTEN_OFF' then
  raise exception 'a written off unit cannot change status'
    using errcode = 'P0001';
end if;
```

Второй прогон сида падал на первой же `WRITTEN_OFF`-единице с `P0001`,
хотя реального изменения не было - переписывалось то же самое значение.
Исправлено `is distinct from` (`20260923140503_fix_tool_units_guard_status_noop.sql`),
тем же приёмом, что уже был в `customers_guard_category` (глава 03) для
"поле действительно изменилось":

```sql
-- стало (верно): терминальность проверяется только при настоящей
-- попытке сменить значение
if old.status = 'WRITTEN_OFF' and new.status is distinct from old.status then
  raise exception 'a written off unit cannot change status'
    using errcode = 'P0001';
end if;
```

Общий вывод не только про этот триггер: у любого поля с "терминальным"
или "неизменяемым" значением стоит сразу спросить не только "какое
новое значение недопустимо", но и "а если пишут то же самое значение
- это тоже нельзя, или можно?". `upsert` и `ON CONFLICT DO UPDATE`
отправляют "то же самое значение" куда чаще, чем кажется на этапе
написания триггера.

**`service_role`, обновляющий `tool_units.status`, неявно требует прав
на `rental_items`.** Тот же прогон сида вскрыл вторую находку до
исправления первой: `tool_units_guard_status` (`security invoker`)
читает `rental_items`, чтобы решить, допустим ли переход, - и делает
это независимо от того, кто именно выполняет `UPDATE tool_units`.
Гранты `service_role` на `tools`/`tool_units` были добавлены сразу
(раздел 4), но `service_role` на `rental_items` - нет, потому что сиду
как будто незачем её трогать напрямую. Триггер на таблице А может
неявно потребовать прав на таблицу Б у *любой* роли, которая когда-либо
напишет в А, даже если сама роль не должна ничего знать о Б. Исправлено
`20260923140417_grant_service_role_select_rental_items.sql` - тот же
выбор, что с `staff` в главе 02 (новая миграция, не правка отправленной).

**`ON CONFLICT DO UPDATE` требует привилегии на все колонки payload, не
только на изменившиеся.** Частный случай той же истории: если бы у
`service_role` не было гранта `update` хотя бы на одну из колонок,
переданных в `upsert()`, отказ был бы на первом слое (`42501`), раньше,
чем дело дойдёт до триггера. В этом проекте `update` на `tool_units`
для `service_role` выдан на все три колонки разом, поэтому до слоя
триггера дело дошло.

## 8. Вопросы для самопроверки

<details>
<summary>Чем частичный уникальный индекс отличается от обычного и какой инвариант держит <code>rental_items_active_unit</code>?</summary>

Обычный <code>unique index</code> запрещает повтор значения во всей
таблице. Частичный добавляет <code>WHERE</code> и запрещает повтор
только среди строк, подходящих под условие. <code>rental_items_active_unit</code>
запрещает больше одной строки с одинаковым <code>tool_unit_id</code>
среди строк с <code>returned_at is null</code> - не больше одной
активной позиции на единицу, при этом история уже возвращённых позиций
по той же единице не ограничена.
</details>

<details>
<summary>Почему вторая параллельная вставка той же единицы в уникальный индекс не падает сразу с ошибкой, а ждёт?</summary>

Postgres не может решить, нарушен ли уникальный индекс, пока не знает
исход первой транзакции - конфликтующая строка ещё не зафиксирована, но
может быть зафиксирована в любой момент. Единственный безопасный
вариант - подождать. После <code>commit</code> первой транзакции вторая
получает <code>23505</code>; после <code>rollback</code> первой -
проходит.
</details>

<details>
<summary>Почему <code>tool_units_guard_status</code> проверяет наличие активной позиции через запрос к <code>rental_items</code>, а не через флаг вроде <code>set_config('app.from_trigger', ...)</code>?</summary>

Флаг сессии (GUC) ничем не защищён - любой <code>authenticated</code>
клиент мог бы выставить его себе сам перед обычным запросом и обойти
правило целиком. Данные в <code>rental_items</code> подделать нечем:
запись туда защищена собственными грантами, политиками, триггерами и
частичным уникальным индексом.
</details>

<details>
<summary>Зачем <code>rental_items_sync_unit</code> объявлена <code>security definer</code>, и почему это не дыра в безопасности?</summary>

Оператор, вставляющий строку в <code>rental_items</code>, не имеет
прав напрямую поменять <code>tool_units.status</code> (грант только у
MANAGER+) или <code>rentals.status</code>/<code>closed_at</code> (эти
колонки вообще не грантованы клиенту). <code>security definer</code>
даёт функции права владельца (<code>postgres</code>) для этой записи.
Не дыра - потому что функция не принимает произвольный ввод от
клиента, а только читает и пишет по данным уже вставленной/изменённой
строки <code>rental_items</code>, которую и так разрешено писать
обычными грантами и политиками оператора.
</details>

<details>
<summary>Почему выдача сделана RPC-функцией, а не серией отдельных <code>INSERT</code> из приложения - и что было бы, если бы RPC был <code>security definer</code>?</summary>

RPC даёт атомарность: аренда и все её позиции - одна транзакция
Postgres, упавшая вставка любой позиции откатывает всё, включая уже
вставленную аренду. Несколько отдельных HTTP-запросов такой гарантии
не дают. Функция объявлена <code>security invoker</code> - она не
меняет права вызывающего, только их атомарность. Будь она
<code>security definer</code>, она перестала бы быть безопасной
демонстрацией "RPC не место, где живут правила": вызывающий получил бы
через неё больше прав, чем у него есть напрямую, и прямой
<code>INSERT</code> в обход RPC перестал бы давать тот же результат.
</details>

<details>
<summary>Почему второй прогон <code>npm run seed:staff</code> сломался на уже применённой миграции, хотя <code>tool_units.status</code> писалось то же самое значение?</summary>

<code>before update of status</code> срабатывает от факта, что колонка
<code>status</code> присутствует в <code>SET</code>, а не от того,
отличается ли новое значение от старого. <code>upsert()</code> с
<code>onConflict</code> формирует <code>ON CONFLICT DO UPDATE</code> со
всеми колонками payload, включая <code>status</code>, даже когда
значение не меняется. Первая версия триггера считала
<code>WRITTEN_OFF</code> терминальным для любого такого
<code>UPDATE</code>, а не только для настоящей попытки сменить статус.
</details>

<details>
<summary>Почему позиция аренды вставляется в открытую аренду политикой, а не триггером - в отличие от <code>customers_guard_category</code> в главе 03?</summary>

У <code>customers_guard_category</code> правило зависело от сравнения
старого и нового значения (<code>OLD</code> нужен). У
<code>INSERT</code> в <code>rental_items</code> нет <code>OLD</code> -
всё необходимое (аренда существует и она <code>ACTIVE</code>)
выражается одним подзапросом прямо в <code>WITH CHECK</code> политики,
без отдельной функции и <code>create trigger</code>.
</details>
