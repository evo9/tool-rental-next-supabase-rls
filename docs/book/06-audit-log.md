# Глава 06. Аудит-лог

## 1. Задача этапа

Любое изменение ключевых таблиц - кто, когда, что именно и с каким
старым/новым значением - должно попасть в единый журнал, который нельзя
подделать и нельзя прочитать никому, кроме суперадмина. Это не "ещё одна
таблица с данными", а требование другого рода: до сих пор в проекте
любая роль, включая `service_role`, могла записать что-то в базу, если у
неё был грант и подходящая политика. Аудит-лог обязан быть недоступен на
запись вообще никому, кроме самой базы, - иначе лог, который можно
подделать, ничего не доказывает.

Второе требование этапа тоньше первого: семь разных таблиц (`staff`,
`tools`, `tool_units`, `customers`, `rentals`, `rental_items`,
`category_grace_periods`) должны логироваться одинаково, без семи копий
почти одинакового кода. И третье - лог обязан честно показывать, кто
именно совершил действие, даже когда оно прошло через триггер, который
сам действует от имени владельца функции (`rental_items_sync_unit` из
главы 04). Если бы лог в этом случае записывал "postgres" вместо
настоящего оператора, он был бы бесполезен для разбора спорных ситуаций
- ровно those случаи, ради которых аудит и заводят.

## 2. Новая механика

### Универсальная триггерная функция на несколько таблиц

Триггерная функция в PL/pgSQL получает контекст вызова через
специальные переменные, которые не нужно объявлять - они всегда
доступны внутри тела:

- `TG_TABLE_NAME` - имя таблицы, на которой сработал триггер;
- `TG_OP` - `'INSERT'`, `'UPDATE'` или `'DELETE'`;
- `TG_ARGV` - массив текстовых аргументов, переданных в `create trigger
  ... execute function f(arg1, arg2, ...)` - у `audit_log_row()` это имя
  колонки первичного ключа;
- `OLD`/`NEW` - старая и новая версия строки (для `INSERT` `OLD` не
  существует, для `DELETE` - `NEW`).

```sql
create trigger audit_tools
    after insert or update or delete on public.tools
    for each row
    execute function public.audit_log_row('id');

create trigger audit_staff
    after insert or update or delete on public.staff
    for each row
    execute function public.audit_log_row('user_id');
```

Одна и та же функция `audit_log_row()` обслуживает обе таблицы (и ещё
пять). Внутри неё `OLD`/`NEW` имеют тип `record`, а не конкретный тип
строки `tools` или `staff`, - поэтому нельзя написать `NEW.name` (какое
имя колонки? у разных таблиц оно разное). Вместо этого - `to_jsonb(NEW)`:
превращает всю строку целиком в один объект `jsonb` с ключами-именами
колонок, не зная заранее, какие это колонки. Имя колонки первичного
ключа для конкретной таблицы передаётся аргументом триггера (`TG_ARGV[0]`)
и используется как ключ в уже готовом `jsonb`, а не как часть SQL-текста -
никакой динамической строки здесь нет, поэтому нет и риска SQL-инъекции
через это имя.

### `security definer`: гранта на запись нет ни у кого

`authenticated` не имеет гранта на `insert` в `audit_log` - его нет
вообще ни у одной роли (раздел 4 ниже). Без `security definer` вставка
внутри триггера падала бы с `42501` сразу после того, как основное
изменение (скажем, `update tools set daily_rate = ...`) уже прошло бы
все свои гранты и политики, - то есть операция откатывалась бы целиком
из-за лога, а не из-за того, что оператор сделал что-то недопустимое.

```sql
create function public.audit_log_row()
    returns trigger
    language plpgsql
    security definer
    set search_path = ''
as $$ ... $$;
```

`security definer` выполняет тело функции с правами того, кто её создал
(`postgres`), а `postgres` - владелец и таблицы `audit_log`, и всех
таблиц, на которые повешены эти триггеры. Владельца объекта гранты и RLS
не касаются вовсе (без `FORCE ROW LEVEL SECURITY`, которая в проекте
нигде не используется) - поэтому вставка проходит, хотя ни у кого из
пользователей приложения нет на неё прав. Это тот же приём, что у
`current_staff_role()` (глава 02, обходит рекурсию RLS на чтение) и у
`rental_items_sync_unit()` (глава 04, пишет в чужие таблицы) - только
здесь "чужая таблица" одна на все семь источников событий.

### `auth.uid()` внутри `security definer` - личность, а не роль исполнения

Это ключевое свойство лога, и оно неочевидно без объяснения, откуда
`auth.uid()` вообще берёт значение. Определение (упрощённо, оно из
схемы `auth`, которую ставит сам Supabase, а не эта миграция):

```sql
create function auth.uid() returns uuid
    language sql stable
as $$
  select nullif(current_setting('request.jwt.claims', true)::json ->> 'sub', '')::uuid
$$;
```

`auth.uid()` читает GUC (session-local настройку) `request.jwt.claims`,
которую PostgREST выставляет один раз в начале запроса из токена
пользователя, - и не трогает `current_user`/`session_user` (SQL-роль,
под которой в данный момент реально выполняется код). Это два независимых
понятия: `current_user` может на время исполнения стать `postgres`
(эффект `security definer`), а `request.jwt.claims` как была выставлена
на весь GUC-контекст соединения в начале запроса, так и остаётся -
`security definer` её не трогает и не может тронуть, потому что она не
про права, а про то, что PostgREST один раз записал в сессию.

Отсюда следствие для этой главы: когда оператор вызывает `issue_rental()`,
и внутри неё `rental_items_sync_unit()` (сама `security definer`, этап
4) от его имени обновляет `tool_units.status`, это обновление поднимает
наш триггер `audit_tool_units`. Тот тоже `security definer`, но
`auth.uid()` внутри него по-прежнему возвращает оператора - не
`postgres` (владельца обеих функций) и не отсутствие личности вообще.
Показано тестом (`tests/policies/06_audit.sql`): запись в логе об
изменении `tool_units.status` на `RENTED` имеет `actor_id` того же
оператора, что и запись о создании самой аренды.

### Запрет записи двумя независимыми слоями

`docs/rls-notes.md` (этап 1) уже объясняет два слоя доступа - грант
решает, можно ли роли вообще тронуть таблицу, RLS решает, какие строки.
У `audit_log` оба слоя закрыты для записи одновременно и независимо:

```sql
revoke all on public.audit_log from anon, authenticated, service_role;
grant select on public.audit_log to authenticated;
alter table public.audit_log enable row level security;
create policy "superadmin reads audit log" on public.audit_log
  for select to authenticated
  using ((select public.current_staff_role()) = 'SUPERADMIN');
-- политик на insert/update/delete нет вообще
```

Одного отсутствия гранта уже достаточно: без гранта `insert` падает с
`42501` до того, как Postgres вообще посмотрит на политики. Но RLS всё
равно включён и политик на запись нет: "RLS включён, подходящей политики
нет - не проходит ничего" (тот же вывод, что в главе 01, раздел
"Политика это разрешение, а не запрет"). Два слоя независимы: если бы
кто-то по ошибке выдал `grant insert ... to authenticated`, отсутствие
политики всё равно блокировало бы запись - опечатка в одном слое не
превращается в дыру, потому что второй слой её не разделяет.

### `service_role` с `BYPASSRLS` тоже не пишет

`service_role` в Supabase имеет атрибут `BYPASSRLS` - для него RLS
не проверяется вовсе, ни на одной таблице. Но `BYPASSRLS` обходит
только один из двух слоёв - тот самый вывод из главы 04
(`docs/rls-notes.md`, "service_role и триггеры, которые он не подозревает,
что заденет"): грант это не заменяет. `revoke all on public.audit_log
from ... service_role` закрывает первый слой, до которого `BYPASSRLS`
не имеет отношения вообще, - `service_role` получает `42501` так же, как
`authenticated` без гранта.

### Действие без пользователя

Скрипт с secret key (`npm run seed:staff`) или прямой SQL от `postgres`
(миграции, SQL Editor) не имеют `request.jwt.claims` в сессии -
`auth.uid()` возвращает `NULL`. Триггер это не считает ошибкой: `actor_id`
и `actor_role` в записи лога получаются `NULL`, что само по себе -
честный ответ "кто это сделал" - "никто из пользователей приложения,
системное действие". Показано тестом на примере фикстуры теста самого
`06_audit.sql`, вставленной от имени `postgres` ещё до первого `act_as`.

## 3. Порядок чтения файлов

1. **`supabase/migrations/20260923175312_audit_log.sql`**, по секциям:
   - **Секция 1, таблица `audit_log`.** `row_pk text`, а не `uuid`, - у
     `category_grace_periods` первичный ключ `category` того же типа,
     что и enum `customer_category`, не `uuid`; общий столбец лога
     должен подходить всем семи таблицам сразу.
   - **Секция 1.1, гранты и политика.** Разобрана в разделе 2 выше
     целиком - оба независимых слоя запрета записи.
   - **Секция 2, `audit_log_row()`.** Смотреть на порядок операций: если
     `TG_OP = 'UPDATE'`, сначала считается `changed_fields` через
     сравнение `jsonb`, и если ничего не изменилось - `return null`
     раньше единственного `insert` в файле, вставки не происходит вообще.
   - **Секция 3, семь `create trigger`.** У каждого - комментарий про
     фазу (`after`) относительно уже существующих `before`-триггеров той
     же таблицы: вопрос алфавитного порядка между `before` и `after`
     не встаёт, фаза важнее алфавита (тот же вывод, что у
     `rental_items_sync_unit` в главе 04).
2. **`tests/policies/06_audit.sql`** - сценарии по ролям. Важнее, чем в
   предыдущих файлах, порядок действий: содержимое `audit_log` можно
   проверить только под `SUPERADMIN` (политика на `select`), поэтому файл
   сначала выполняет действия под `OPERATOR`/`MANAGER`, а затем
   переключается на `admin@example.com`, чтобы прочитать, что записалось -
   не тот же самый пользователь, который действие совершил (разобрано в
   разделе 7, это стоило одного прогона впустую при написании теста).

## 4. Решения и альтернативы

**Одна функция на семь таблиц, а не семь похожих функций.** Строение
строки разное у каждой таблицы, но структура работы с ней - одна и та же:
собрать `old`/`new` в `jsonb`, найти изменённые колонки, вставить запись.
`to_jsonb(row)` и `TG_ARGV` делают эту работу таблично-независимой -
писать семь функций означало бы семь копий одной и той же логики
сравнения `jsonb`, отличающихся только тем, какая колонка - первичный
ключ. Цена решения - функция ничего не знает о смысле конкретной
таблицы (не может, например, специально отформатировать что-то только
для `rentals`); для аудита это не нужно, ему важен факт изменения, а не
его бизнес-смысл.

**`changed_fields` считается сравнением `jsonb`, а не по факту наличия
колонки в `SET`.** `update of <col>` (использованный в триггерах глав
3-5) срабатывает от присутствия колонки в `SET`, не от того, изменилось
ли значение, - это уже дважды приводило к находкам в этом проекте
(`customers_guard_category` в главе 03, `tool_units_guard_status` в
главе 04). Здесь та же ловушка была бы куда заметнее: `after insert or
update or delete` без `of <col>` означает, что триггер срабатывает на
любой `UPDATE`, включая `upsert` сида, где `ON CONFLICT DO UPDATE`
формирует `SET` со всеми колонками payload независимо от того, изменилось
ли хоть одно значение. Сравнение `jsonb`-значений `NEW`/`OLD` по каждому
ключу - единственный надёжный способ отличить настоящее изменение от
no-op записи того же самого значения, а не полагаться на то, какие
колонки клиент перечислил в запросе.

**`actor_id` без внешнего ключа на `staff`.** Казалось бы естественным
`references public.staff (user_id)`, но `staff` (глава 02) разрешает
`SUPERADMIN` удалять чужие строки (`"staff: superadmin deletes others"`).
Внешний ключ с поведением по умолчанию (`ON DELETE NO ACTION`) заблокировал
бы такое удаление навсегда, как только у сотрудника появится хоть одна
запись в логе, - а `ON DELETE SET NULL` тихо стёр бы историческую
принадлежность действия. Ни то, ни другое не годится: лог обязан
пережить оргштатные изменения, не блокируя их и не теряя данные. Имя
сотрудника для интерфейса `/audit` поэтому получают отдельным запросом
(`src/features/audit/queries.ts`, `listAuditLog`) по собранному списку
`actor_id`, а не через embedding PostgREST, которому как раз и нужен
настоящий внешний ключ, чтобы понять связь.

**`security invoker` не рассматривался для `audit_log_row()`.** В
отличие от `rentals_guard_customer`/`rental_items_set_daily_rate` (главы
4-5), где `security invoker` был осознанным выбором ("вызывающему и так
всё это разрешено, поднимать права незачем"), здесь `security invoker`
в принципе не сработал бы: `authenticated` не имеет гранта на `insert` в
`audit_log` ни при каких условиях, вставка от его имени упала бы с
`42501` во всех случаях без исключения. Выбора между двумя рабочими
вариантами не было - `security definer` здесь не стиль, а единственный
способ вообще что-то записать.

## 5. Как повторить с нуля

```bash
npm run db:new audit_log
# вписать SQL: таблица audit_log, индексы, гранты и политика (только
# SELECT для SUPERADMIN), функция audit_log_row(), семь триггеров

npm run db:push
npm run db:types
```

Предусловие - этапы 0-5 уже применены (нужны все семь аудируемых
таблиц, в том числе `category_grace_periods` из главы 05). Сид (`npm run
seed:staff`) продолжает работать без изменений - он лишь начинает
попутно наполнять `audit_log` при каждой вставке/апдейте `tools`/
`tool_units`/`staff`/`customers`, включая молчаливый пропуск записи для
no-op `UPDATE` при повторном запуске (раздел 4 выше).

Руками, что не покрыто автоматическими тестами:

- **Понять, почему `auth.uid()` внутри `security definer` возвращает
  оператора, а не владельца функции.** Раздел 2, подраздел "личность, а

- **В интерфейсе.** `/audit` доступен и виден только суперадмину
  (у остальных ролей пункт меню скрыт); фильтры по таблице, сотруднику
  и датам сужают список; раскрытие записи по клику показывает diff
  изменённых колонок для `UPDATE` и полный снимок для `INSERT`/`DELETE`.

## 7. Грабли

**Первая версия теста проверяла содержимое `audit_log`, оставаясь под
той же ролью, что совершила действие.** `tests/policies/06_audit.sql`
изначально выполнял `issue_rental()` под `OPERATOR`, а сразу следующим
шагом, всё ещё под `OPERATOR`, проверял через `JOIN`, что в логе
появилась ожидаемая запись, - и тест падал с `FAIL: ожидалось 1 строк,
получено 0`, хотя отладочный запрос напрямую (от имени `postgres`,
минуя RLS) показывал, что нужная запись в таблице действительно есть,
с правильным `actor_id`. Причина - политика "superadmin reads audit
log" не пропускает `OPERATOR` ни к одной строке, включая ту, которую он
сам только что породил своим действием: писать в лог и читать из него -
две разные операции с двумя разными требованиями к роли, и одно не даёт
права на другое. Починка - переставить проверки содержимого лога под
`admin@example.com` (`SUPERADMIN`), оставив под `OPERATOR`/`MANAGER`
только проверку, что для них `select * from audit_log` пуст. Вывод для
любого будущего теста аудита: "автор действия" и "тот, кто может увидеть
его в логе", в этом проекте - две разные роли почти всегда, порядок
`act_as(...)` в тесте должен это отражать, а не молчаливо предполагать,
что тот, кто написал, может и прочитать.

## 8. Вопросы для самопроверки

<details>
<summary>Почему одна и та же функция <code>audit_log_row()</code> может обслуживать семь разных таблиц с разными наборами колонок?</summary>

Она не обращается к колонкам по имени - `to_jsonb(NEW)`/`to_jsonb(OLD)`
превращают строку любой структуры в объект `jsonb` с ключами-именами
колонок, а `TG_ARGV[0]` (аргумент конкретного `create trigger`) даёт имя
колонки первичного ключа именно той таблицы, на которой сработал
триггер. Функция работает с данными как с набором пар ключ-значение, не
зная заранее, какие это ключи.
</details>

<details>
<summary>Почему <code>audit_log_row()</code> обязана быть <code>security definer</code>, и не является ли это дырой в безопасности?</summary>

У <code>authenticated</code> нет гранта на <code>insert</code> в
<code>audit_log</code> ни при каких условиях - без <code>security
definer</code> запись не прошла бы вообще, что сломало бы саму операцию,
которую логируют. Не дыра - потому что функция не принимает произвольный
ввод от клиента, только пишет то, что и так уже стало содержимым
<code>NEW</code>/<code>OLD</code> строки, которую вызывающий и так менял
собственными, отдельно проверенными грантами и политиками.
</details>

<details>
<summary>Почему <code>auth.uid()</code> внутри триггера, вызванного другим <code>security definer</code>-триггером, всё ещё возвращает исходного пользователя?</summary>

<code>auth.uid()</code> читает GUC <code>request.jwt.claims</code>,
выставленный один раз PostgREST в начале запроса, а не
<code>current_user</code> (эффективную SQL-роль исполнения, которая
действительно меняется под <code>security definer</code>). Личность
вызывающего и роль, с правами которой сейчас выполняется код, - два
независимых понятия.
</details>

<details>
<summary>Почему для запрета записи в <code>audit_log</code> недостаточно только отсутствия гранта или только отсутствия политики - нужны оба?</summary>

Формально достаточно одного отсутствующего гранта: без него
<code>42501</code> случается раньше, чем Postgres вообще посмотрит на
политики. Но оба слоя всё равно включены независимо - если бы кто-то по
ошибке выдал грант на запись, отсутствие политики на <code>insert</code>/
<code>update</code>/<code>delete</code> заблокировало бы её точно так же.
Один слой не должен быть единственной защитой от ошибки в другом.
</details>

<details>
<summary>Почему <code>service_role</code> не может записать в <code>audit_log</code>, хотя у него есть <code>BYPASSRLS</code>?</summary>

<code>BYPASSRLS</code> отключает только проверку политик - второй слой.
Грант на <code>insert</code> (первый слой) у <code>service_role</code>
тоже отсутствует (<code>revoke all ... from ... service_role</code>), и
до этого слоя <code>BYPASSRLS</code> не имеет отношения вообще - отказ
происходит на нём, до всякого RLS.
</details>

<details>
<summary>Почему <code>row_pk</code> хранится как <code>text</code>, а не как <code>uuid</code>?</summary>

У шести из семи таблиц первичный ключ действительно <code>uuid</code>,
но у <code>category_grace_periods</code> это <code>category</code> -
значение enum <code>customer_category</code>. Общий столбец лога должен
подходить всем таблицам сразу, значит его тип - наименьший общий
знаменатель, <code>text</code>, куда приводится любое значение через
<code>-&gt;&gt;</code> на уже собранном <code>jsonb</code>.
</details>

<details>
<summary>Почему у <code>audit_log.actor_id</code> нет внешнего ключа на <code>staff.user_id</code>?</summary>

<code>SUPERADMIN</code> может удалить чужую строку <code>staff</code>
(глава 02). Внешний ключ с поведением по умолчанию заблокировал бы такое
удаление, как только у сотрудника появится хоть одна запись в логе, а
<code>ON DELETE SET NULL</code> стёр бы историческую принадлежность
действия. Лог обязан пережить оргштатные изменения - имя сотрудника для
интерфейса поэтому получают отдельным запросом, а не через
PostgREST-embedding, которому нужен настоящий внешний ключ.
</details>
