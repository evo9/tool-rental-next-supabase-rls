# Глава 00. Поднять и осмотреться

## 1. Задача этапа

Прежде чем писать первую таблицу, нужна база, к которой можно применять
миграции, и понимание того, что в этой базе уже есть до нашего кода:
какие схемы существуют, кто их создал, какими ключами к ним обращаются
и что произойдёт, если довериться настройкам Supabase по умолчанию не
глядя. Этот этап не содержит ни одной миграции - он про инфраструктуру
и решения, от которых зависят все следующие этапы.

Главное решение этапа - облачный проект вместо локального стека в Docker,
и явное отключение автоматических грантов, на которых основана вся модель
доступа проекта.

## 2. Новая механика

### Supabase CLI как dev-зависимость

Supabase CLI (`supabase`) - не глобальный инструмент, а пакет в
`devDependencies` (`package.json`). Причина простая: версия CLI влияет на
формат сгенерированных типов и на то, какие флаги команд доступны. Если
ставить его глобально, у двух разработчиков могут оказаться разные версии
и разное поведение `db:push` без единой причины в git-истории. Через
`devDependencies` версия зафиксирована в `package-lock.json`, как у любой
другой библиотеки. Все команды в проекте идут через npm-скрипты
(`npm run db:push` и т.д.), а не через `supabase ...` напрямую, - это тот
же CLI, вызванный так, чтобы использовалась версия из `node_modules`, а не
что попало в `$PATH`.

### Облачный проект вместо локального стека

Официальный флоу Supabase - `supabase start`, который поднимает Postgres,
GoTrue (Auth), PostgREST, Storage API и Studio в Docker локально. В этом
проекте локальный стек не используется: миграции применяются сразу к
облачному проекту (`npm run db:push`), а `supabase start` не запускается
вообще.

Причина - место на диске. Локальный стек Supabase - это восемь-десять
Docker-образов (Postgres, GoTrue, PostgREST, Storage, Realtime, Studio,
Kong и другие), каждый по несколько сотен мегабайт, плюс тома с данными.
На разработческой машине с ограниченным диском это ощутимая цена за
удобство, которого для учебного проекта не требуется: миграции применяются
к локальной и к облачной базе одинаково, а тестовые пользователи и так
создаются через Admin API (`npm run seed:staff`), не через
`supabase db seed`.

Цена решения: нет `supabase db reset` с мгновенным пересозданием базы из
пустоты за секунды - `npm run db:reset` пересоздаёт именно облачную базу
и делает это дольше, поэтому запрещён без прямой просьбы (раздел
"Окружение" `CLAUDE.md`). Тестировать миграции локально, не трогая
демонстрационные данные в облаке, тоже нельзя - придётся быть аккуратнее
с содержимым миграций до `db:push`.

### `supabase link` и что он сохраняет

```bash
npx supabase login
npx supabase link --project-ref <ref>
```

`link` не отправляет в базу никаких изменений - он просто говорит CLI,
какой облачный проект имеется в виду, когда локально запускают `db:push`,
`db:reset` или `db:types`. Результат сохраняется в `supabase/.temp/`:
`project-ref`, версии Postgres и сервисов, адрес пулера соединений. Эта
папка перечислена в `supabase/.gitignore` вместе с `.env.local` - в ней
нет секретов (сам project-ref не секрет), но она специфична для машины,
на которой выполнили `link`, и клонировавшему репозиторий её нужно
получить самому командой `link`, а не унаследовать из git.

### История применённых миграций

`db:push` не сравнивает файлы в `supabase/migrations/` с текущей схемой
таблиц - он сравнивает их с таблицей истории, которую сам Supabase CLI
создаёт в облачной базе при первом использовании миграций
(`supabase_migrations.schema_migrations`, отдельная служебная схема, не
`public`). Каждая успешно применённая миграция добавляет туда строку с
версией - той же меткой времени, что в имени файла. При следующем
`db:push` CLI берёт список локальных файлов, вычитает те версии, что уже
есть в этой таблице, и применяет только разницу, по возрастанию версии.

Отсюда два следствия, важных для этого проекта:

- у `db:push` нет отдельного шага "проверить, изменился ли файл" - меняется
  только *набор* версий, а не их содержимое. Если руками поправить SQL уже
  применённой миграции и снова сделать `db:push`, CLI не увидит разницы и
  ничего не применит: версия уже отмечена как применённая;
- чтобы всё же повторно выполнить уже применённый (и при этом идемпотентный)
  файл, версию нужно явно снять с отметки: `supabase migration repair
  --status reverted <версия>`. Это правит только историю в облаке, сам SQL
  не откатывает - подробный разбор, когда так можно делать, а когда нет, в
  главе 02, раздел "Грабли".

### Схемы `public` / `auth` / `storage`

Облачный проект Supabase - это один Postgres со несколькими схемами,
управляемыми разными частями платформы:

- **`public`** - обычная схема приложения. Всё, что создаём миграциями
  этого проекта (`tools`, `staff`, `customers`, ...), живёт здесь.
- **`auth`** - управляется GoTrue (сервисом аутентификации). Таблица
  `auth.users` - источник истины о том, кто вошёл; `auth.uid()` в
  политиках читает `id` текущего пользователя оттуда же. Эту схему проект
  не меняет своими миграциями, только читает (`current_staff_role()`
  делает `where s.user_id = auth.uid()`).
- **`storage`** - управляется Storage API. Таблица `storage.objects` -
  метаданные загруженных файлов (какой бакет, какой путь, кто и когда
  загрузил), а сами файлы лежат отдельно, не в Postgres. RLS на этой
  таблице работает точно так же, как на любой таблице в `public`, - и
  именно так в главе 03 устроен доступ к фото клиентов: через обычные
  `create policy` на `storage.objects`.

PostgREST (слой, который превращает HTTP-запросы браузера в SQL) по
умолчанию видит только схемы из `api.schemas` в `supabase/config.toml`
(`public` и `graphql_public`) - `auth` и `storage` наружу как REST не
торчат, к ним обращаются через отдельные клиенты Supabase SDK
(`supabase.auth.*`, `supabase.storage.*`), которые ходят к GoTrue и
Storage API напрямую, а не через PostgREST.

### Publishable и secret ключи

У проекта два ключа, и разница между ними - это разница между "какая роль
Postgres выполнит запрос" и "будет ли вообще применяться RLS":

- **publishable** (`NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, формат
  `sb_publishable_...`) - предназначен для браузера, поэтому попадает в
  клиентский бандл (префикс `NEXT_PUBLIC_` в Next.js как раз это и
  означает). Запрос с этим ключом без сессии выполняется под ролью
  `anon`, с валидной сессией - под `authenticated`. RLS применяется
  в обоих случаях.
- **secret** (`SUPABASE_SECRET_KEY`, формат `sb_secret_...`) - только для
  сервера: скрипты (`scripts/seed-staff.ts`) и в перспективе route
  handlers, которым нужен полный доступ. Запрос выполняется под ролью
  `service_role`, у которой атрибут `BYPASSRLS` - политики не
  применяются вообще. Грант на таблицу этой роли всё равно нужен
  (`BYPASSRLS` обходит политики, а не гранты) - это видно в
  `20260918155352_grants_service_role.sql` из главы 02.

  В коде приложения secret-ключ не используется: `src/lib/supabase/admin.ts`
  существует только для скриптов и явно помечен в `CLAUDE.md` как объект,
  который нельзя импортировать из кода, попадающего в клиентский бандл.

Это новый формат ключей Supabase: старые проекты используют `anon` и
`service_role` - непрозрачные JWT, подписанные одним общим секретом.
Publishable и secret ключи не JWT, их нельзя декодировать как токен, и
их можно перевыпускать по отдельности, не инвалидируя весь проект.

### Почему `sb_publishable_` передаётся и в `apikey`, и в `Authorization`

PostgREST и Storage API ожидают два заголовка с разным назначением:
`apikey` - подтверждает, что запрос вообще имеет право обращаться к API
этого проекта (шлюз Supabase сверяет его с ключами, выданными проекту, и
пропускает или отклоняет запрос целиком, до PostgREST), `Authorization:
Bearer <token>` - несёт то, под какой ролью запрос выполнится в Postgres
(её оттуда же берёт `auth.uid()` и весь остальной SQL). Старый
anon-ключ был JWT с полезной нагрузкой вида `{"role": "anon"}`, и его
можно было подставить в оба заголовка сразу: шлюз проверял его как
`apikey`, а PostgREST, декодируя его же как `Authorization`, доставал
роль `anon` прямо из содержимого токена.

`sb_publishable_`-ключ не JWT и не содержит роли внутри себя - его
нельзя декодировать, чтобы получить `anon`. Пока у пользователя нет
своей сессии, `@supabase/ssr` всё равно подставляет один и тот же
publishable-ключ в оба заголовка, и запрос выполняется под ролью
`anon` - но эту роль в данном случае определяет не содержимое токена
(его там нет), а то, что Supabase на своей стороне узнаёт сам
publishable-ключ и сопоставляет его с `anon`, а не декодирует. После
входа `Authorization` заменяется на access token пользователя (роль
`authenticated`), а `apikey` остаётся тем же publishable-ключом - он
и раньше отвечал не за роль, а за то, что запрос вообще принадлежит
этому проекту.

```bash
# без сессии: apikey и Authorization - один и тот же publishable-ключ,
# роль запроса - anon
curl -i "https://<ref>.supabase.co/rest/v1/tools?select=*" \
  -H "apikey: sb_publishable_..." \
  -H "Authorization: Bearer sb_publishable_..."
```

### Отключённые авто-гранты

При создании таблицы в новом проекте Supabase по умолчанию есть
настройка Dashboard "Automatically expose new tables via API", включающая
автоматическую выдачу `select`/`insert`/`update`/`delete` ролям `anon` и
`authenticated` на каждую новую таблицу и `execute` роли `public` (то
есть всем, включая `anon`) на каждую новую функцию. С этой настройкой
первый слой доступа (гранты) фактически выключен для всех новых объектов,
и вся защита держится на одном RLS - забытая политика на insert открывает
таблицу на запись кому угодно.

В этом проекте настройка отключена в Dashboard. Каждая новая таблица,
последовательность и представление получает гранты явно, миграцией
(пример - `grant select on public.tools to authenticated;` в
`20260917211501_create_tools.sql`); то же для `execute` на функциях -
Postgres выдаёт его `public` по умолчанию для новых функций независимо
от этой настройки Dashboard, и его приходится отзывать самим
(`revoke execute ... from public`) в каждой миграции с функцией
(разобрано в главе 02). Как выглядит запрос без нужного гранта и с ним -
глава 01, раздел "Два слоя доступа".

## 3. Порядок чтения файлов

У этого этапа нет миграции - реализация распределена по конфигурации
и настройкам облачного проекта, которые не лежат в репозитории построчно.
Смотреть стоит на:

1. **`package.json`, секция `scripts`** - весь набор команд, через которые
   идёт работа с базой (`db:new`, `db:push`, `db:types`, `db:reset`,
   `seed:staff`). Обратить внимание, что `supabase` - в `devDependencies`,
   а не глобальный пакет.
2. **`supabase/.gitignore`** - `.temp` и `.branches` (артефакты `link`,
   специфичные для машины) и `.env.local` (ключи) исключены из git.
   Это то, что клонировавший репозиторий обязан создать/получить сам:
   `link` для первого, собственный `.env.local` для второго.
3. **`supabase/config.toml`, секция `[api]`** - `schemas = ["public",
   "graphql_public"]`, то, какие схемы PostgREST отдаёт наружу. Файл в
   целом описывает локальный стек, который в проекте не запускается
   (`supabase start` не используется), но секция `[api]` актуальна и для
   облачного проекта - те же настройки видны в Dashboard.
4. **`.env.local`** (не в git, создаётся вручную по этому списку) -
   `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`,
   `SUPABASE_SECRET_KEY`, `SEED_PASSWORD` - пароль тестовых пользователей
   для `seed:staff`, `DB_URL` - строка подключения для `psql`, которой
   гоняются SQL-тесты (раздел "Окружение" `CLAUDE.md`).

## 4. Решения и альтернативы

**Облачный проект вместо `supabase start`.** Альтернатива - локальный
стек в Docker, дающий мгновенный `db reset` и работу офлайн. Отклонено
из-за места на диске, которое эти образы занимают, и потому что для
учебного проекта воспроизводимость важнее скорости пересоздания базы: тот,
кто клонирует репозиторий, повторяет ровно те же шаги (`link`,
`db:push`, `seed:staff`) что и на облаке, что и локально были бы теми же.

**Новый формат ключей вместо legacy anon/service_role JWT.** Legacy-ключи
- это самоподписанные JWT на одном общем секрете проекта; скомпрометированный
`service_role` ключ старого формата требует перевыпуска всего JWT-секрета,
что инвалидирует и `anon`-ключ разом. Publishable и secret ключи
перевыпускаются по отдельности. Цена - они не декодируются как обычный
JWT и не несут читаемой полезной нагрузки, что не мешает проекту: код
нигде не парсит сам ключ, только передаёт его SDK.

**Явные гранты вместо авто-экспозиции таблиц.** Альтернатива - оставить
"Automatically expose new tables" включённой и полагаться только на
RLS. Отклонено: два независимых слоя (грант + политика) надёжнее одного
- если политику по ошибке когда-нибудь расширят до `to public`, `anon`
всё равно не пройдёт дальше гранта. Цена - для каждой новой таблицы,
последовательности, представления и функции нужен явный `grant` в
миграции; это несложно забыть, поэтому стандарт комментирования SQL
(`CLAUDE.md`) требует секции с грантами в каждой миграции, создающей
объект.

## 5. Как повторить с нуля

1. Создать проект на supabase.com (Dashboard), выбрать регион.
2. В настройках Dashboard отключить "Automatically expose new tables via
   API" и самостоятельную регистрацию через Auth (`enable_signup` - её
   включают обратно только когда до этого дойдёт своя фича).
3. Создать Next.js проект: `npx create-next-app --src-dir`, добавить
   Tailwind и shadcn/ui по их собственным гайдам.
4. Поставить Supabase CLI как dev-зависимость: `npm install --save-dev
   supabase`.
5. Добавить npm-скрипты из `package.json` этого проекта (`db:new`,
   `db:push`, `db:types`, `db:reset`, `seed:staff`).
6. `npx supabase login`, затем `npx supabase link --project-ref <ref>` -
   `<ref>` виден в адресе проекта в Dashboard.
7. В Dashboard → Project Settings → API скопировать publishable и
   secret ключи, создать `.env.local` по списку из раздела 3.
8. `supabase/.gitignore` уже создаётся командой `supabase init`/`link`
   автоматически - проверить, что в нём есть `.temp` и `.env.local`.

## 6. Как проверить

```bash
# link прошёл: файл появился и содержит непустой project-ref
cat supabase/.temp/project-ref

# история миграций существует и пуста (до первой миграции этапа 1)
npm run db:push
# ожидается: сообщение, что применять нечего (миграций ещё нет в
# supabase/migrations/) либо явный список из нуля файлов

# ключ проверяется прямым запросом к PostgREST под ролью anon:
# таблиц ещё нет, но заголовок должен быть принят (не 401 из-за
# неправильного ключа, а 404/структурная ошибка из-за отсутствия таблицы)
curl -i "https://<ref>.supabase.co/rest/v1/" \
  -H "apikey: <publishable>" -H "Authorization: Bearer <publishable>"
```

Ручная проверка: открыть Dashboard → Database → Roles и убедиться, что
`anon`, `authenticated`, `service_role` существуют без выданных прав на
несуществующие пока таблицы (гранты появятся в главе 01).

## 7. Грабли

**`db:push` без `link` падает с ошибкой о недостающем проекте.** CLI не
знает, к какой базе применять миграции, пока не выполнен `supabase link`.
Чинится самим `link`; ошибка не про credentials, а именно про отсутствие
привязки.

**Ожидание, что `db:push` перевыполнит изменённый, но уже применённый
файл.** История хранит версии, не хэши содержимого (раздел 2 выше). Правка
уже отправленной миграции без `migration repair` молча ничего не
применяет - выглядит так, будто изменения "не сработали", хотя на самом
деле они не пытались примениться.

**Secret-ключ, случайно попавший в код, который бандлится для браузера.**
В Next.js файл без `'use server'` и без явной серверной границы может
попасть в клиентский JS, если на него ссылается серверный и клиентский
код одновременно через общий модуль. Проверяется сборкой и поиском по
`.next` (`CLAUDE.md`, раздел "Никогда"); `admin.ts` с secret-ключом
поэтому используется только напрямую из скриптов, не через `features/`.

**Оставленная включённой "Automatically expose new tables".** Тихая
проблема: всё продолжает работать (RLS всё ещё фильтрует строки), пока
кто-то не напишет таблицу без политики на запись - и тогда она окажется
открыта на запись любому `authenticated`, а не только явно перечисленным
ролям. Отключается один раз, до первой миграции, в Dashboard.

## 8. Вопросы для самопроверки

<details>
<summary>Почему в проекте не используется <code>supabase start</code>?</summary>

Локальный стек в Docker занимает много места на диске (восемь-десять
образов), а миграции и так применяются напрямую к облачному проекту без
разницы в поведении. Цена - нет мгновенного `db reset` и работы офлайн.
</details>

<details>
<summary>Что именно сохраняет <code>supabase link</code> и почему эта папка не коммитится?</summary>

Ссылку на проект (`project-ref`), версии сервисов и адрес пулера - в
`supabase/.temp/`. Не коммитится, потому что специфична для машины,
на которой выполнили `link`; каждый, кто клонирует репозиторий, получает
её заново командой `link`.
</details>

<details>
<summary>Как <code>db:push</code> определяет, какие миграции уже применены?</summary>

Supabase CLI хранит список применённых версий миграций в служебной схеме
в самой облачной базе (`supabase_migrations.schema_migrations`). `db:push`
сравнивает локальные файлы с этим списком по версии (метке времени в
имени файла) и применяет только те, которых там ещё нет - содержимое
файла не сравнивается, только факт применения версии.
</details>

<details>
<summary>Чем publishable-ключ отличается от secret-ключа?</summary>

Publishable - для браузера, запрос идёт под ролью <code>anon</code> или
<code>authenticated</code>, RLS применяется. Secret - только для сервера,
запрос идёт под <code>service_role</code>, у которой атрибут
<code>BYPASSRLS</code>, и политики не применяются вообще (гранты при этом
по-прежнему нужны).
</details>

<details>
<summary>Почему до входа в систему publishable-ключ передаётся и в заголовке <code>apikey</code>, и в <code>Authorization</code>?</summary>

<code>apikey</code> подтверждает право запроса обращаться к API проекта,
<code>Authorization</code> определяет роль, под которой он выполняется.
До логина роли ещё нет, кроме <code>anon</code>; publishable-ключ не JWT
и не содержит роли внутри, поэтому роль <code>anon</code> определяется
не декодированием токена, а тем, что Supabase узнаёт сам ключ. Один и
тот же ключ годится в оба заголовка, потому что до входа никакого
другого "токена" у запроса и нет. После входа <code>Authorization</code>
заменяется на access token пользователя, а <code>apikey</code> остаётся
публикуемым ключом проекта.
</details>

<details>
<summary>Что делает отключённая в проекте настройка "Automatically expose new tables" и почему она отключена?</summary>

Она автоматически выдаёт гранты <code>anon</code> и <code>authenticated</code>
на каждую новую таблицу. С ней первый слой доступа фактически выключен,
и вся защита держится на одном RLS. Отключена, чтобы гранты выдавались
явно миграциями - независимый второй слой защиты на случай ошибки в
политике.
</details>

<details>
<summary>Какие три схемы Postgres задействует Supabase и за что каждая отвечает?</summary>

<code>public</code> - объекты приложения, создаются миграциями проекта.
<code>auth</code> - управляется GoTrue, источник <code>auth.users</code>
и <code>auth.uid()</code>. <code>storage</code> - управляется Storage API,
метаданные файлов в <code>storage.objects</code>, сами файлы лежат
отдельно от Postgres.
</details>
