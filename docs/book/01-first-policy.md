# Глава 01. Одна таблица и первая политика

## 1. Задача этапа

Первая таблица (`tools` - модель инструмента) и первая политика: любой
залогиненный читает, никто не пишет. Само правило простое, но на нём
разбирается механика, на которой держится весь проект: чем grant
отличается от RLS-политики, почему отказ в доступе на чтение выглядит
не как ошибка, а как пустой список, и как в Next.js получить серверную
сессию Supabase, не читая её из localStorage.

Здесь же появляются страница входа и список инструмента - минимальный
сквозной путь: запрос из браузера доходит до Postgres, проходит через
оба слоя доступа и возвращается назад.

## 2. Новая механика

### Два слоя доступа: GRANT и RLS

К таблице с RLS запрос проверяется дважды, и это два независимых
механизма Postgres:

1. **GRANT** - решает, может ли роль (`anon`, `authenticated`,
   `service_role`) вообще выполнять операцию над таблицей. Это обычные
   привилегии Postgres, существовавшие задолго до RLS.
2. **RLS-политика** - решает, какие конкретно строки эта роль увидит
   или сможет изменить, при условии что первый слой пройден.

```sql
alter table public.tools enable row level security;

grant select on public.tools to authenticated;

create policy "authenticated can read tools"
on public.tools for select
to authenticated
using (true);
```

Без `grant select` запрос от `authenticated` упадёт с `42501 permission
denied for table tools`, даже не дойдя до политики `using (true)`. С
грантом, но без политики (или с `using (false)`) запрос выполнится
успешно и вернёт `200` с пустым массивом - Postgres не находит ни одной
строки, разрешённой политикой, что для него не отличается от `where
false`. Оба слоя должны совпасть, чтобы строки дошли до клиента.

### Почему RLS возвращает пустой массив, а не ошибку

RLS в Postgres реализован как неявный `WHERE`, а не как проверка,
предшествующая запросу. Когда на таблице включён RLS, к каждому запросу
дописывается условие: строка видна, если хотя бы одна применимая
политика возвращает `true` (политики одного действия объединяются через
`OR`). Если политик нет или ни одна не подходит, эффективное условие -
`where false` для всех строк. Это совершенно обычный, синтаксически
корректный SQL-запрос, который просто ничего не находит - у Postgres нет
причины возвращать ошибку, как её не возвращает `select * from tools
where false` без всякого RLS.

Это осознанное поведение, не побочный эффект: клиент не может отличить
"таблица пуста" от "у меня нет прав видеть её строки", и это правильно -
ответ не раскрывает даже сам факт существования данных. Запись ведёт
себя иначе: `insert`, у которого новая строка не проходит `with check`,
падает с ошибкой `42501 new row violates row-level security policy`, а
не молча ничего не делает - скрывать отказ в записи смысла нет, клиент и
так знает, что он отправлял (эта асимметрия подробнее в главе 02, раздел
про `USING` и `WITH CHECK`).

| Ситуация | HTTP | Тело |
|---|---|---|
| Нет grant | 401 | `42501 permission denied for table ...` |
| Есть grant, нет подходящей политики, select | 200 | `[]` |
| Есть grant, нет подходящей политики, insert | 401 | `42501 new row violates row-level security policy` |

### `@supabase/ssr` и серверная сессия через куки

Сессия Supabase (access token + refresh token) в этом проекте живёт в
куках, а не в `localStorage`. Причина - архитектурная: страницы
рендерятся на сервере (React Server Components), а серверный рендер
выполняется раньше, чем в браузере отработает хоть одна строка JS, то
есть до того, как стал бы доступен `localStorage`. Куки же приходят с
каждым HTTP-запросом, включая самый первый.

`@supabase/ssr` даёт два фабричных клиента - `createBrowserClient` и
`createServerClient` - которые отличаются именно источником кук:
браузерный читает `document.cookie` сам, серверному источник кук нужно
передать явно (объект `cookies` с `getAll`/`setAll`).

```ts
// минимальная идея server.ts - полный код в разделе 3
const supabase = createServerClient(url, key, {
  cookies: {
    getAll: () => cookieStore.getAll(),
    setAll: (list) => list.forEach(c => cookieStore.set(c.name, c.value, c.options)),
  },
})
```

**`getUser()`, а не `getSession()`.** `getSession()` только разбирает
куку и верит её содержимому - кука приходит от клиента, доверять ей на
сервере нельзя. `getUser()` дополнительно ходит в Auth-сервер и проверяет
подпись токена. На сервере всегда используется `getUser()`.

### `proxy.ts`

`src/proxy.ts` - обязательное имя файла для Next.js middleware в проекте
с `--src-dir` (в корне проекта Next его не найдёт). Он выполняется до
рендера любой страницы и делает две вещи разом: обновляет протухший
access token, обращаясь к Auth-серверу (`supabase.auth.getUser()` внутри
`proxy.ts` - именно тот вызов, что освежает токен), и редиректит на
`/login`, если пользователя нет.

Ключевая деталь реализации - `setAll` в `proxy.ts` пишет обновлённые
куки в двух местах: в сам `request` (чтобы их увидел последующий рендер
той же страницы) и в новый `response` (чтобы их сохранил браузер). Если
вместо этого просто вернуть свежесозданный `NextResponse.next()` без
перенесённых кук, обновление токена потеряется и пользователя будет
разлогинивать примерно раз в час - по сроку жизни access token'а. Это
частая ошибка в связке Next.js + Supabase, воспроизводимая не сразу
(токен живёт долго), поэтому легко пропустить при беглом тестировании.

Редирект в `proxy.ts` - это удобство интерфейса, а не защита данных:
он просто отправляет на страницу входа того, у кого нет сессии. Настоящая
защита - RLS: даже если кто-то обратится к REST API Supabase напрямую,
минуя Next.js и `proxy.ts` целиком, без сессии политика на чтение не
отдаст ни одной строки.

### Три клиента Supabase

В `src/lib/supabase/` - три фабрики клиента, разделённые по тому, откуда
и с какими правами идёт запрос:

- **`server.ts`** - сессионный клиент для серверных компонентов, server
  actions и route handlers. Читает сессию из кук запроса, запрос к базе
  идёт от имени вошедшего пользователя, RLS работает. Это основной
  клиент проекта - им сделаны все запросы из `features/*/queries.ts` и
  `features/*/actions.ts`.
- **`client.ts`** - браузерный клиент, тоже сессионный (та же сессия, что
  видит сервер, но через `document.cookie`). Нужен там, где запрос должен
  выполниться прямо в браузере, - в этом проекте это загрузка файлов
  напрямую в Storage (глава 03), а не запросы к таблицам `public`.
- **`admin.ts`** - клиент с secret-ключом, роль `service_role`, `RLS`
  обходится полностью. Используется только в скриптах вне кода
  приложения (`scripts/seed-staff.ts`); в код, который может попасть
  в клиентский бандл, не импортируется никогда (`CLAUDE.md`, раздел
  "Никогда").

Разница между `server.ts` и `client.ts` - не в том, какие у них права
(права у обоих определяет сессия пользователя, оба ходят под
`authenticated` после входа), а в том, откуда они берут эту сессию:
`server.ts` - из кук запроса на сервере, `client.ts` - из кук в браузере.
`admin.ts` отличается по существу: у него нет и не может быть сессии
пользователя, он всегда `service_role`.

## 3. Порядок чтения файлов

1. **`supabase/migrations/20260917211501_create_tools.sql`** - таблица
   `tools`, включение RLS, первый грант, первая политика. Смотреть на
   порядок: `enable row level security` идёт раньше `grant` и `create
   policy` в файле, но порядок этих трёх операторов друг относительно
   друга не важен - все три обязательны, а не последовательны по смыслу.
2. **`supabase/migrations/20260918084456_grant_anon_read_tools.sql`** и
   **`20260918084642_revoke_anon_read_tools.sql`** - демонстрационная пара:
   первая специально выдаёт `anon` доступ к первому слою, чтобы увидеть
   RLS "в чистом виде" (второй слой отсекает, `[]`, `200`), вторая
   отзывает его обратно - рабочее состояние проекта не пускает `anon` к
   данным точки проката вообще, доступ отсекается уже на первом слое,
   не доходя до политик. Комментарий во второй миграции объясняет, зачем
   обе оставлены в истории, а не схлопнуты в одну: это записанный
   эксперимент, а не два шага одного решения. Разбор результата -
   `docs/rls-notes.md`, раздел "Два слоя доступа".
3. **`src/lib/supabase/server.ts`**, **`client.ts`**, **`admin.ts`** - три
   клиента из раздела 2 выше. У `server.ts` обратить внимание на
   `try/catch` вокруг `setAll`: вызов из серверного компонента, где куки
   уже частично отправлены и писать в них нельзя, - это не ошибка, а
   ожидаемая ситуация (обновлением токена в этом случае занимается
   `proxy.ts`, который выполняется раньше).
4. **`src/proxy.ts`** - обновление сессии и редирект, разобраны в разделе 2.
5. **`src/app/(auth)/login/actions.ts`** и **`page.tsx`** - вход через
   server action: `signInWithPassword` возвращает общую фразу об ошибке
   вместо "такого email нет" - не подсказывает, существует ли аккаунт.
6. **`src/app/(app)/layout.tsx`** - вторая проверка сессии, уже после
   `proxy.ts`: на неё полагается весь код внутри layout, `user` в нём
   гарантированно есть. Редирект в `proxy.ts` защищает не от всех
   случаев - например, `proxy.ts` мог не сработать при статической
   отдаче исключённых путей (`config.matcher`).
7. **`src/features/tools/queries.ts`** - первый содержательный запрос
   к таблице с RLS: `throw error` только для настоящих ошибок (нет
   гранта, сеть), пустой результат из-за RLS - это просто `[]`, не
   `error`.

## 4. Решения и альтернативы

**Демо-миграции `grant_anon_read_tools` / `revoke_anon_read_tools`
оставлены в истории, а не отменены одним файлом.** Альтернатива - вообще
не проводить эксперимент миграцией, а проверить поведение RLS вручную
через SQL Editor и не оставлять следов в `supabase/migrations/`. Отклонено:
история миграций - часть документации репозитория (раздел "Как устроены
миграции" в `docs/book/README.md`), и то, что можно увидеть в двух
последовательных файлах, нагляднее пересказа в тексте.

**`getUser()` вместо `getSession()` на сервере.** Единственный
правильный вариант для доверенной проверки - `getSession()` быстрее (без
похода к Auth-серверу), но проверяет только структуру куки, не подпись;
для чтения данных, защищённых RLS, использование непроверенной сессии
не даёт защиты сверх той, что уже даёт сам RLS, но ломает предположение
"`user` в серверном коде достоверен" везде, где на него полагаются
(например, редирект в `layout.tsx`).

**Обновление сессии в `proxy.ts`, а не при каждом запросе к базе
отдельно.** Альтернатива - обновлять токен лениво, прямо в `server.ts` при
обнаружении, что он истёк. Отклонено: `proxy.ts` выполняется до рендера
любой страницы ровно один раз за запрос, что даёт единственное место для
записи обновлённых кук; при ленивом обновлении из нескольких серверных
компонентов пришлось бы решать, кто из них имеет право писать куки
(в общем случае - никто, см. `try/catch` в `server.ts`).

## 5. Как повторить с нуля

```bash
npm run db:new create_tools
# вписать SQL из раздела 3, пункт 1
npm run db:push
npm run db:types
npm run dev
```

Дальше - зарегистрировать тестового пользователя (Dashboard → Authentication
→ Add user, самостоятельная регистрация отключена, раздел
"Отключённые авто-гранты" главы 00 - тот же принцип, доступ создаётся
вручную, а не открытой формой), вставить строку-другую в `tools` через
SQL Editor (`insert into public.tools (name, daily_rate, deposit_value)
values ('Перфоратор', 250, 3000);`), открыть `/login`, войти, увидеть
список на `/tools`.

## 6. Как проверить

Для этого этапа выделенного файла в `tests/policies/` ещё нет (тесты в
этом формате начинаются с этапа 2, когда появляются роли, которые есть
что сравнивать) - проверка на этом этапе ручная, через `curl`:

```bash
# без сессии: anon отсекается на гранте, не на политике
curl -i "https://<ref>.supabase.co/rest/v1/tools?select=*" \
  -H "apikey: <publishable>" -H "Authorization: Bearer <publishable>"
# ожидается: 401, 42501 permission denied for table tools

# с access token'ом вошедшего пользователя
curl -i "https://<ref>.supabase.co/rest/v1/tools?select=*" \
  -H "apikey: <publishable>" -H "Authorization: Bearer <access_token>"
# ожидается: 200 и строки, добавленные вручную
```

`access_token` берётся из куки `sb-<ref>-auth-token` после входа в
интерфейсе, либо через `supabase.auth.signInWithPassword` в консоли
браузера. Готово, когда: список виден только после входа, а прямой
запрос без сессии не может обойти это через REST API.

## 7. Грабли

**`NextResponse.next()` без перенесённых кук в `proxy.ts` -> разлогин раз
в час.** Токен обновляется, но обновление никуда не сохраняется -
воспроизводится не сразу, потому что access token живёт достаточно
долго, чтобы это не заметить при быстром тестировании. Чинится переносом
кук в оба места, как описано в разделе 2.

**`proxy.ts` в корне проекта вместо `src/`.** Next.js с `--src-dir`
ищет middleware только рядом с `app/`, то есть в `src/`. Файл в корне
просто не подхватывается, без явной ошибки - редиректа на `/login`
не происходит, но и защиты нет ни от чего, кроме RLS.

**`getSession()` вместо `getUser()` в серверном коде.** Не даёт немедленно
видимой ошибки: интерфейс продолжает работать, потому что данные всё
равно защищены RLS. Ломается предположение, что `user` на сервере
достоверен, - тихая проблема, которая не проявится, пока кто-то не
подделает куку с валидной структурой, но неверной подписью.

**`anon`, оставленный с доступом к `tools` после демонстрации.** Если
забыть применить `revoke_anon_read_tools.sql` (или отменить его),
проект остаётся в демонстрационном состоянии - `anon` проходит первый
слой и получает `[]` только потому, что для него нет политики; стоит
кому-то добавить политику `to public` по ошибке, и данные точки проката
станут доступны без всякой сессии.

## 8. Вопросы для самопроверки

<details>
<summary>Что произойдёт при запросе к таблице с RLS, если grant есть, а подходящей политики нет?</summary>

Запрос выполнится успешно: <code>select</code> вернёт <code>200</code> и
пустой массив, <code>insert</code>/<code>update</code>/<code>delete</code>
вернёт ошибку <code>42501</code> (для insert - потому что новую строку
некуда "спрятать", для update/delete в отсутствие <code>using</code> -
0 затронутых строк, а не ошибка, если только не задан <code>with
check</code>, который и даёт ошибку).
</details>

<details>
<summary>Почему пустой результат из-за RLS - это <code>200</code>, а не <code>403</code>?</summary>

RLS реализован как неявный <code>WHERE</code>, дописываемый к запросу, а
не как проверка перед его выполнением. Запрос, у которого условие
сводится к <code>where false</code>, для Postgres синтаксически корректен
и просто не находит строк - это не отличается от любого другого запроса
с пустым результатом.
</details>

<details>
<summary>Почему на сервере используется <code>getUser()</code>, а не более быстрый <code>getSession()</code>?</summary>

<code>getSession()</code> разбирает куку без проверки подписи - кука
приходит от клиента, доверять ей на сервере нельзя. <code>getUser()</code>
дополнительно обращается к Auth-серверу и проверяет подпись токена.
</details>

<details>
<summary>Зачем в <code>proxy.ts</code> обновлённые куки записываются и в <code>request</code>, и в <code>response</code>?</summary>

В <code>request</code> - чтобы их увидел рендер той же страницы дальше по
цепочке. В <code>response</code> - чтобы их сохранил браузер. Без записи
в <code>response</code> обновление токена теряется, и пользователя
разлогинивает по истечении access token'а.
</details>

<details>
<summary>Чем отличаются друг от друга три клиента Supabase в проекте?</summary>

<code>server.ts</code> и <code>client.ts</code> - оба сессионные (RLS
работает), различаются только источником кук (сервер против браузера).
<code>admin.ts</code> - secret-ключ, роль <code>service_role</code>, RLS
обходится полностью; используется только в скриптах, не в коде
приложения.
</details>

<details>
<summary>Почему редирект в <code>proxy.ts</code> называется "удобством, а не защитой"?</summary>

Он работает только внутри Next.js-приложения и решает, какую страницу
показать. Настоящая защита данных - RLS в Postgres: запрос к REST API
Supabase напрямую, минуя Next.js целиком, без сессии всё равно не получит
строк, потому что не пройдёт политику.
</details>
