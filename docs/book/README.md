# Книга: система проката инструмента на Supabase

Пошаговый разбор учебного проекта: прокат инструмента на Next.js и Supabase,
с упором на RBAC и RLS на уровне Postgres. Книга написана по тому же коду,
который лежит в этом репозитории, - в ней нет ничего, чего нельзя увидеть
в `supabase/migrations/`, `tests/policies/` и `src/`.

## Для кого эта книга

Для разработчика, который знает SQL и Postgres, но видит Supabase и RLS
впервые. Она не объясняет базовый SQL (`select`, `create table`) и не
объясняет React или Next.js с нуля - объясняет то, что специфично для связки
Supabase + RLS + серверный Next.js: как политики решают, какие строки видны;
как сессия живёт в куках, а не в localStorage; как устроено приватное
хранилище файлов.

Прочитав главы по порядку, можно повторить проект с нуля на собственном
облачном проекте Supabase и понимать каждую строку SQL, которая при этом
выполняется.

## Как читать

Каждая глава `NN-slug.md` соответствует одному этапу проекта
(`docs/tz/tz-plan.md` описывает все этапы,
`docs/progress.md` - что из них сделано). Главы читаются
по порядку: каждая следующая опирается на механику из предыдущих и не
повторяет то, что уже объяснено.

Внутри главы - восемь разделов в фиксированном порядке:

1. **Задача этапа** - что реализуем и зачем, в двух-трёх абзацах.
2. **Новая механика** - каждое новое понятие этапа с нуля, с минимальным
   примером.
3. **Порядок чтения файлов** - в каком порядке открывать файлы этапа
   (миграции, тесты, TypeScript) и на что смотреть в каждом. Если в самом
   файле объяснения не хватает, оно даётся здесь, с указанием, к какому
   месту файла относится.
4. **Решения и альтернативы** - какие варианты рассматривались, почему выбран
   этот, что было бы при другом выборе.
5. **Как повторить с нуля** - команды и шаги от пустой миграции до рабочего
   состояния этапа.
6. **Как проверить** - команды тестов и ручные проверки, ожидаемый результат.
7. **Грабли** - реальные ошибки этапа: текст, SQLSTATE, причина, починка.
8. **Вопросы для самопроверки** - 5-8 вопросов, ответы скрыты под `<details>`.
   Стоит попробовать ответить, не открывая, - если вопрос не поддаётся,
   это повод перечитать раздел 2 этой же главы.

Главу читают не отдельно от кода: раздел 3 каждой главы - это список файлов
с пояснениями, их и открывают параллельно с текстом.

## Как устроены миграции

Все изменения схемы - только файлы в `supabase/migrations/`, с именем вида
`<timestamp>_<slug>.sql`. Правка через Studio не воспроизводится у другого
разработчика, поэтому не используется вообще. Список миграций, уже
применённых к облачной базе, Supabase CLI хранит в самой базе (подробнее -
глава 00, раздел "История применённых миграций"); `db:push` сравнивает его
с локальными файлами и применяет только новые.

Одна миграция обычно закрывает один логический кусок этапа, но у этапа может
быть несколько миграций подряд, если что-то вскрылось уже после применения
первой (пример - миграции про `service_role` в главе 02). Откатывать
применённую миграцию нельзя, только исправлять следующей. Каждая миграция
начинается с шапки: что делает, от чего зависит, как проверить.

## Как устроены тесты

`tests/policies/NN_slug.sql` проверяет политики этапа `NN`: заходит под
тремя тестовыми сотрудниками и под анонимным пользователем и для каждого
действия проверяет ожидаемый результат - разрешено, пусто или конкретная
ошибка. Весь файл выполняется внутри `begin; ... rollback;`, поэтому не
оставляет данных в базе. Запускается через `psql` (команда - в разделе
"Окружение" `CLAUDE.md`) или целиком в SQL Editor. Новый этап добавляет
новый файл и не трогает старые; при прогоне всех файлов по порядку старые
тесты должны продолжать проходить - иначе это регрессия.
