# Глава 07. Дашборд, единицы, импорт, QR

## 1. Задача этапа

До этого этапа у приложения нет главного экрана, который отвечает на
вопрос "что сейчас происходит на точке": сколько единиц свободно, сколько
на руках, сколько недоступно и списано, сколько аренд открыто и сколько
из них просрочено. Эти числа должны показываться только сотрудникам:
человек, вошедший в систему, но не заведённый в `staff`, не должен узнать
даже, сколько у точки инструмента.

Второе требование - завести в систему уже существующий парк. Вводить
сотни единиц руками нереально, поэтому менеджер загружает CSV-файл,
сохранённый из Excel, и получает отчёт: сколько строк вставлено и какие
не вставились (с номером строки и причиной). Одна плохая строка не должна
отменять остальные, а повторная загрузка того же файла не должна портить
данные: все строки вернутся как дубликаты, и в базе ничего не изменится.

Третье - привязать физическую вещь к записи в системе. На каждую единицу
печатается наклейка с QR-кодом, который любая камера телефона открывает как
ссылку на карточку единицы. Отсюда же управление единицами: список
единиц модели, добавление, смена статуса, списание, карточка единицы с
историей аренд.

Главная тема этапа - как не потерять RLS там, где в запросе появляется
посредник (view, функция импорта, route handler). В каждом из этих мест
есть очевидный способ сделать так, что права базовых таблиц перестанут
работать, и этот способ нужно уметь распознать.

## 2. Новая механика

### `view` и права владельца: ловушка обхода RLS

Обычный `view` в Postgres не хранит данные, он хранит запрос. Но выполняется
этот запрос **с правами владельца view**, а не того, кто из него читает.
Владелец view - тот, кто выполнил `create view` (в миграциях это
`postgres`), а `postgres` владеет и всеми таблицами проекта. К владельцу
таблицы RLS не применяется (это тот же факт, на котором держится
`current_staff_role()` в главе 02: без `FORCE ROW LEVEL SECURITY` политики
владельца не касаются).

Отсюда ловушка. Допустим, есть view поверх `tool_units`:

```sql
create view public.counts as
select count(*) as available from public.tool_units where status = 'AVAILABLE';
grant select on public.counts to authenticated;
```

Пользователь без строки в `staff` не видит ни одной строки `tool_units`
напрямую: политика "staff can read tool units" его не пропускает. Но через
`counts` он получит настоящее число: запрос внутри view выполняет владелец,
для которого политик нет. Грант на view открыл то, что политики таблицы
закрывали. Тест этапа показывает это на копии view без опции: один и тот же
пользователь получает `0` строк из таблицы и `>= 3` доступных единиц из view.

Лекарство - опция `security_invoker`:

```sql
create view public.counts
with (security_invoker = true)
as
select count(*) as available from public.tool_units where status = 'AVAILABLE';
```

С ней запрос внутри view выполняется так, как будто вызывающий написал его
сам: проверяются его права на базовые таблицы и его RLS. Опция появилась в
Postgres 15, в облачном проекте стоит 17. Что получают роли от
`dashboard_counts`:

| Кто читает | Результат | Где отказ |
|---|---|---|
| активный сотрудник, любая роль | реальные числа | - |
| вошёл, но нет строки в `staff` | одна строка из нулей | политики базовых таблиц |
| `anon` | `42501` | нет гранта на view, отказ до RLS |

Почему нули, а не пустой результат: агрегат `count(*)` без `group by` всегда
возвращает ровно одну строку, даже если считать нечего. Политика отфильтровала
все строки таблицы, `count` от пустого набора - ноль. Для интерфейса это
удобно (не нужно обрабатывать пустой ответ), для безопасности достаточно: цифр
точки такой пользователь не узнаёт.

Проверка на будущее: любой новый `view` в проекте либо создаётся с
`security_invoker = true`, либо нужен осознанный довод, почему нет.

### Route handler в App Router

До сих пор изменения данных шли через server actions (функции с
`'use server'`, которые форма вызывает как обычную функцию). Route handler -
другой инструмент: файл `src/app/api/.../route.ts`, который экспортирует
функции с именами HTTP-методов и возвращает обычный HTTP-ответ.

```ts
// src/app/api/example/route.ts
export async function POST(request: Request) {
    const form = await request.formData();
    const file = form.get('file');
    if (!(file instanceof File)) {
        return Response.json({ error: 'No file' }, { status: 400 });
    }
    return Response.json({ size: file.size });
}
```

Чем он отличается от server action. Action привязан к форме или к
вызову из клиентского компонента, и Next сам решает транспорт; результат
возвращается как значение функции, а не как HTTP-ответ с выбранным кодом
статуса. Route handler - это обычный адрес: у него свой метод, свои коды
ответа (400 на плохой файл, 403 роль, 413 слишком большой), его можно
вызвать `curl`-ом и проверить без браузера.

Почему для загрузки файла выбран он. Загрузке нужен контроль над
ответом: размер файла нужно проверить до чтения содержимого и ответить
`413`, формат - `400`, отсутствие прав - `403`. Кроме того, ответ - это
структурированный отчёт (сколько вставлено, таблица ошибок), а не переход по
странице; такой ответ естественнее отдавать JSON-ом с кодом статуса. И, наконец,
проверяемость: `curl -F file=@tests/fixtures/import-sample.csv` без браузера.
Сессия при этом никуда не девается: route handler читает те же cookies, а
клиент `createClient()` из `src/lib/supabase/server.ts` - тот же сессионный,
от имени пользователя.

### Подтранзакции в plpgsql: `begin ... exception ... end`

В `plpgsql` блок с секцией `exception` работает как **savepoint**
(подтранзакция): при входе в блок Postgres запоминает состояние, а если внутри
блока возникла ошибка, откатывает всё, что блок успел записать, и
передаёт управление обработчику. Внешняя транзакция при этом продолжается.

```sql
for v_row in select * from jsonb_array_elements(p_rows) loop
  begin
    insert into public.tool_units (...) values (...);
    v_inserted := v_inserted + 1;
  exception when others then
    v_errors := v_errors || jsonb_build_array(
      jsonb_build_object('code', sqlstate, 'message', sqlerrm));
  end;
end loop;
```

Что происходит при выполнении. Пять строк, третья дубликат: первые две
вставились, третья упала на `23505`, откатилась только она и ушла в
`v_errors`, четвёртая и пятая вставились. В конце вызова всё, что не
откатилось, фиксируется вместе с внешней транзакцией. Если бы блока не было,
ошибка третьей строки отменила бы весь вызов, включая две уже вставленные.

Два следствия, которые нужно знать.

1. Откатывается состояние базы, но **не локальные переменные plpgsql**.
   Если внутри блока `v_inserted` увеличен, а следом упала ошибка,
   переменная останется увеличенной. Поэтому счётчик успехов в функции
   стоит последним оператором блока (после него ошибки быть не может), а номер
   строки присваивается первым (обработчику он нужен).
2. Откат захватывает всё, что строка сделала, а не только последний оператор.
   Если строка успела создать модель, а потом единица упала на дубле
   номера, модель тоже откатывается: остаётся либо всё, либо ничего. Тест
   проверяет именно этот сценарий.

Цена: каждый блок с `exception` - отдельная подтранзакция, и на десятках тысяч
строк это заметно. Для файла в сотни строк несущественно; размер файла
ограничивает route handler.

### `security invoker` у RPC импорта и роль в route handler

Функция `import_tool_units` объявлена `security invoker`, как `issue_rental` в
главе 04: каждая её вставка проходит гранты, политики и триггеры вызывающего.
Права вставлять определяют политики `"tools: manager+ inserts"` и
`"manager+ can insert tool units"`. Оператор, вызвавший функцию напрямую
через `supabase.rpc(...)`, получит отчёт, где каждая строка упала с `42501`, и
ни одной вставленной строки.

Значит проверка роли в route handler (`OPERATOR` получает `403` до чтения
файла) - это UX: быстрый и понятный ответ вместо отчёта из сотни одинаковых
ошибок. Защиты она не даёт и не должна давать: даже если проверку убрать или
обойти, запрос всё равно идёт сессионным клиентом, и политики в базе отклонят
его. Так же устроены скрытые пункты меню в главе 03b: интерфейс подсказывает,
база решает.

### Уникальный индекс по выражению

Импорт находит модель по названию, но названия в файле набирают руками:
"Перфоратор", "перфоратор " (пробел на конце) и "ПЕРФОРАТОР" - одна модель.
Обычный `unique (name)` посчитал бы их тремя разными. Поэтому индекс строится не
по колонке, а по выражению:

```sql
create unique index tools_name_normalized_key
  on public.tools (lower(btrim(name)));
```

Индекс хранит результат выражения и следит за его уникальностью. Запрос
использует его, только если выражение в `where` совпадает с выражением
индекса слово в слово (`where lower(btrim(name)) = lower(btrim(...))`).
`on conflict (lower(btrim(name)))` так же ссылается на индекс через
выражение. Нарушитель получает `23505` с именем ограничения
`tools_name_normalized_key`.

`lower()` зависит от локали базы: здесь `en_US.UTF-8`, и кириллица
приводится к нижнему регистру. В базе с локалью `C` "Дрель" и "дрель"
остались бы разными строками.

## 4. Решения и альтернативы

**Просрочка в дашборде без учёта grace.** Счётчик `overdue_rentals`
считает аренды со статусом `ACTIVE` и `planned_return_at < now()`. Это то же
правило, что в `isOverdue()` интерфейса и в комментарии к `rental_status`
(глава 04). Grace period из главы 05 решает, когда начнёт начисляться
доплата, но не отменяет того факта, что инструмент уже должен быть
возвращён. Если считать просрочкой только время после grace, счётчик на
дашборде разошёлся бы с красным бейджем `Overdue` в списке аренд: одна и та
же аренда в одном месте просрочена, в другом нет.

**View, а не функция с проверкой роли.** Альтернатива - RPC
`security definer`, которая сама проверяет `current_staff_role()` и считает
числа мимо RLS. Работает, но это ручная защита: каждую такую функцию нужно
помнить проверять, и она снова знает о таблицах то, что уже знают политики.
`security_invoker`-view не содержит ни одной проверки роли: всю работу делают
политики базовых таблиц, и новая роль или изменение политики сразу
отражаются на дашборде.

**Единицу можно завести только как `AVAILABLE` или `UNAVAILABLE`.**
Триггер `tool_units_guard_status` срабатывает на `update of status`, на
вставку он не смотрит. Для защиты вставки выбрана политика `WITH CHECK`, а
не второй триггер: у `INSERT` нет `OLD`, а условие относится только к новой
строке, - то же рассуждение, что для `"staff can add items to active
rentals"` в главе 04. Без правки политики `MANAGER` мог бы вставить
единицу `RENTED` без аренды: инвариант "`RENTED` = есть активная позиция"
сломался бы, а счётчик `rented` на дашборде разошёлся бы с числом аренд.
Правка сделана новой миграцией (`drop policy if exists` + `create
policy`), исходная миграция главы 04 не переписывалась. Сид не затронут:
он работает под `service_role`, у которого `BYPASSRLS`.

**Импорт: подтранзакция на строку, а не `on conflict do nothing` и не
"всё или ничего".** Три варианта.

- Одна вставка `insert ... select ... on conflict do nothing`. Быстро, но
  дубликаты пропускаются молча: в отчёте нельзя показать, какая строка и
  почему не вставилась, а это требование этапа.
- Одна транзакция без блока `exception`. Первая же ошибка отменяет весь
  файл. Для сотни строк, где одна опечатка в инвентарном номере, это
  неприемлемо.
- Блок `begin ... exception` на строку (выбрано). Каждая строка ведёт
  себя как отдельная операция, ошибка возвращается с номером строки и
  SQLSTATE. Цена - подтранзакция на строку, для сотен строк несущественная.

`exception when others` ловит любую ошибку строки, в том числе ошибку
программиста в самой функции: она тоже уйдёт в отчёт, а не уронит вызов.
Поэтому в отчёте остаются и `code`, и `message`: ошибка в функции не
маскируется, а видна в таблице ошибок. Отмену запроса (`57014`) блок не ловит.

**Существующая модель не меняется импортом.** Если модель с таким названием уже
есть, тариф и залог из файла для неё игнорируются, единица привязывается к
существующей. Импорт заводит единицы, а цену модели меняют осознанно через
`tools` (`UPDATE`, `MANAGER` и выше). Иначе загрузка файла с устаревшим тарифом
молча переписала бы цены, а уже выданные аренды здесь ни при чём (у них
снимок тарифа, глава 05), но новые получили бы неверную цену.

**Формат проверяется в TypeScript, но не только там.** Разбор и проверка формата
(`papaparse` и `zod`: число, пустые поля, допустимый статус) идут до базы и
дают ошибки с номером строки без единого обращения к Postgres. Но функция
`import_tool_units` не полагается на это: приведение типов и ограничения
таблиц ловят то же самое ещё раз, и такая строка попадёт в отчёт, а не
уронит вызов. Пользовательское приложение - не единственный возможный
клиент RPC.

**Как читается файл из Excel.** Разделитель определяется по строке заголовка
(что чаще, `;` или `,`), а не по всему файлу: в заголовке нет чисел, а в теле
запятая может быть десятичной (`250,00`), и автоопределение по всему файлу
могло бы ошибиться. Десятичная запятая допускается: Excel в этих локалях
пишет так. BOM отбрасывается. Кодировка: файл, сохранённый как "CSV
UTF-8", читается как UTF-8; сохранённый как просто "CSV" Excel в русской
локали пишет в Windows-1251, поэтому при невалидном UTF-8 используется
Windows-1251, а не показывается набор нечитаемых символов.

**QR содержит URL, а не инвентарный номер.** Номер пришлось бы читать
отдельным приложением-сканером, которое знает, что с ним делать. URL
(`${NEXT_PUBLIC_APP_URL}/units/<id>`) открывает любая камера телефона без
дополнительных программ, а в карточке единицы сотрудник уже вошёл в систему
(без входа сработает переадресация на `/login`). В коде используется `id`, а не
номер: номер можно исправить, а наклейка с ним уже напечатана. Цена - ссылка
привязана к адресу приложения: наклейки, напечатанные с адресом
`localhost`, за пределами компьютера разработчика не откроются, поэтому
`NEXT_PUBLIC_APP_URL` для проверки с телефона указывается адресом в локальной
сети (`http://<IP компьютера>:3000`, тот же, что в `allowedDevOrigins`).

**SVG на сервере.** Пакет `qrcode` строит SVG-строку в серверном компоненте:
в браузер уходит готовая разметка без клиентской библиотеки, и та же
разметка без изменений печатается на наклейке.

## 5. Как повторить с нуля

1. Миграция: `npm run db:new dashboard_and_import`, содержимое - четыре секции
   из раздела 3. До `db:push` убедитесь, что в `tools` нет двух моделей с
   одинаковым `lower(btrim(name))`, иначе создание индекса упадёт с `23505`:

   ```sql
   select lower(btrim(name)), count(*) from public.tools
   group by 1 having count(*) > 1;
   ```
2. `tests/policies/07_dashboard_import.sql`, затем `npm run db:push`.
3. Все SQL-тесты по порядку (команда - раздел 6). Упал старый тест - это
   регрессия, разбираться нужно с ним.
4. `npm run db:types`: в `src/types/database.ts` появятся `dashboard_counts` и
   `import_tool_units`.
5. Пакеты: `npm install papaparse zod qrcode` и
   `npm install -D @types/papaparse @types/qrcode`. Перезапустите dev-сервер.
6. Код из раздела 3 в том порядке, в каком он там перечислен: сначала разбор
   и route handler (проверяются `curl`, см. ниже), затем страницы.
7. В `.env.local` задайте `NEXT_PUBLIC_APP_URL` (для проверки QR с телефона -
   адрес в локальной сети, `http://<IP компьютера>:3000`).

## 6. Как проверить

**SQL-тесты.** Файлы этапов 2-7 по порядку. С `psql`:

```bash
set -a; source .env.local; set +a
for f in tests/policies/0[2-7]_*.sql tests/pricing/05_calc.sql; do
  psql "$DB_URL" -v ON_ERROR_STOP=1 -f "$f"
done
```

Без `psql`: `npx supabase db query --linked -f tests/policies/07_dashboard_import.sql`.
Успех - команда завершилась без ошибки, провал - ошибка с текстом `FAIL: ...`.
Через `db query` не видно построчных `NOTICE ok`, только итог.

**Типы и сборка.** `npx tsc --noEmit`, `npm run lint`, `npm run build` - без
ошибок.

**Route handler без браузера.** Эндпоинту нужна cookie сессии, поэтому проще
проверять через интерфейс, но ответы можно посмотреть и `curl`-ом, если взять
cookie из браузера:

| Запрос | Ожидание |
|---|---|
| без сессии | `307` на `/login` (это делает `proxy.ts`) |
| оператор | `403`, `{"error":"Only a manager or above can import tools."}` |
| менеджер, без файла | `400` |
| менеджер, файл без нужных колонок | `400`, `Missing column(s): ...` |
| менеджер, `?mode=preview`, `tests/fixtures/import-sample.csv` | `200`, `totalRows: 6`, `validRows: 5`, ошибка формата в строке 5 |
| менеджер, `?mode=import`, тот же файл, первый раз | вставлено 4, ошибки: строка 5 (формат), строка 7 (`23505`) |
| то же, второй раз | вставлено 0, все строки в ошибках |

Результат проверки этапа: обе таблицы в БД совпали с отчётом (файл-пример
дал модель с двумя единицами и повторный импорт ничего не изменил).

**Вручную.**

- `/dashboard` от разных ролей: числа одинаковы, у `OPERATOR` то же самое.
- `/tools/<id>`: форма добавления и кнопки статуса видны `MANAGER`, у
  `OPERATOR` их нет; списание просит подтверждения.
- `/units/<id>`: кнопка "Issue" у свободной единицы ведёт на
  `/rentals/new?unit=<id>` с предвыбранной единицей, "Accept return" у
  выданной - в карточку аренды.
- Импорт файла, сохранённого из Excel с кириллицей; повторный импорт того же
  файла.
- Печать наклеек: `/tools/print-labels?tool=<id>`, Ctrl+P, в предпросмотре
  только сетка наклеек, без меню.
- Сканирование наклейки телефоном (нужен `NEXT_PUBLIC_APP_URL` с адресом в
  локальной сети). Если телефон ещё не вошёл в систему, откроется `/login`,
  а после входа - главная, не карточка единицы.

## 7. Грабли

**Переменная plpgsql переживает итерацию цикла.** Модель предыдущей строки
осталась бы в `v_tool_id`, и строка, где `select` ничего не нашёл, вставила бы
единицу к чужой модели. В функции `v_tool_id := null` стоит в начале блока
каждой строки.

**`on conflict` не находит индекс.** Ошибка `there is no unique or exclusion
constraint matching the ON CONFLICT specification`, если выражение в
`on conflict (...)` не совпадает с выражением индекса. Индекс построен по
`lower(btrim(name))`, значит и в `on conflict`, и в поиске нужно писать ровно
так.

**Excel и числа с запятой.** `250,00` в файле с разделителем `;` - обычное
дело, а `zod` с `z.number()` его отвергнет. Число принимается строкой,
запятая заменяется на точку, потом проверяется формат.

**Excel и кодировка.** "CSV UTF-8" приходит с BOM, просто "CSV" в русской
локали - в Windows-1251. Без запасного разбора вместо названий получаются
последовательности вида `Ð”Ñ€ÐµÐ»ÑŒ`.

**Типы `supabase-js` и склеенная строка в `select`.** Тип результата
выводится из литерала строки. `'a, ' + 'b(c)'` для TypeScript - обычный
`string`, и результат превращается в `GenericStringError`. Длинный select
пишется одним литералом (можно в обратных кавычках, с переносами строк).

**Типы view nullable.** `supabase gen types` не знает, что `count(*)` не бывает
`null`, и все колонки `dashboard_counts` получаются `number | null`. Приведение
`?? 0` - в одном месте, в `queries.ts`.

**Dev-сервер, запущенный до установки пакетов.** Страницы, использующие новый
пакет (`qrcode`), отвечали `404` на старом процессе `next dev`, а на свежей
сборке (`npm run build` и `next start`) работали. После `npm install` dev-сервер
нужно перезапустить.

**Сессия и `/api`.** `proxy.ts` перенаправляет на `/login` любой запрос без
сессии, в том числе к `/api/...`: `curl` без cookie получает `307`, а не
`401`. Ответ `401` из route handler виден только в случае, когда прокси
пропустил запрос.

**Ссылка в QR и `localhost`.** Наклейка, напечатанная со страницы,
открытой по `http://localhost:3000`, содержит адрес, который телефон не
откроет. Адрес берётся из `NEXT_PUBLIC_APP_URL`, а если она не задана - из
заголовков текущего запроса (при открытой с компьютера странице это как раз
`localhost`).

## 8. Вопросы для самопроверки

1. Чем отличается результат `select * from dashboard_counts` для
   залогиненного пользователя без строки в `staff` и для `anon`? На каком слое
   защиты происходит каждый отказ?

   <details>
   <summary>Ответ</summary>

   Первый получает одну строку из нулей: грант на view у `authenticated` есть,
   а политики базовых таблиц с `security_invoker` не пропускают ни одной строки,
   `count(*)` по нулю строк даёт `0`. Второй получает `42501`: у `anon` нет
   гранта на view, отказ происходит на слое грантов, до RLS.
   </details>

2. View создан без `security_invoker`, владелец - `postgres`. Пользователь без
   `staff` читает его. Что он увидит и почему?

   <details>
   <summary>Ответ</summary>

   Реальные числа. Запрос внутри view выполняется с правами владельца, а
   владелец таблицы не подчиняется RLS (нет `FORCE ROW LEVEL SECURITY`). Грант
   на view открыл то, что политики таблиц закрывали.
   </details>

3. Строка импорта создала новую модель, а вставка единицы упала на дубле
   инвентарного номера. Что останется в базе и почему?

   <details>
   <summary>Ответ</summary>

   Ничего от этой строки. Блок `begin ... exception ... end` - подтранзакция:
   при ошибке откатывается всё, что блок записал, в том числе модель. Остальные
   строки не затронуты.
   </details>

4. Счётчик `v_inserted` увеличивается последним оператором блока. Что
   изменится, если поставить его первым?

   <details>
   <summary>Ответ</summary>

   Строка, упавшая после увеличения, останется посчитанной как вставленная:
   откат подтранзакции восстанавливает состояние базы, но не локальные
   переменные plpgsql. Отчёт соврёт о количестве вставленных строк.
   </details>

5. Оператор обошёл проверку роли в route handler и вызвал RPC напрямую. Что
   произойдёт?

   <details>
   <summary>Ответ</summary>

   Функция `security invoker` выполнит вставки от его имени, политики
   `"tools: manager+ inserts"` и `"manager+ can insert tool units"` отклонят
   каждую строку с `42501`. Вызов завершится отчётом `inserted: 0` и ошибкой
   `42501` на каждой строке. Проверка роли в handler - UX, защита в базе.
   </details>

6. Зачем в миграции этапа 7 заменена политика INSERT на `tool_units`, если
   триггер `tool_units_guard_status` уже следит за статусом?

   <details>
   <summary>Ответ</summary>

   Триггер срабатывает на `update of status`, на вставку нет. Без правки политики
   менеджер мог бы вставить единицу сразу в статусе `RENTED` без единой аренды, и
   счётчик `rented` разошёлся бы с реальными арендами.
   </details>

7. Почему в QR-коде лежит URL с `id`, а не инвентарный номер?

   <details>
   <summary>Ответ</summary>

   URL открывает любая камера телефона без отдельного сканера, а номер пришлось
   бы читать специальным приложением. `id` не меняется, а номер можно
   исправить после печати наклейки.
   </details>

8. Почему `lower(btrim(name))` в индексе и в поиске по модели должны быть
   записаны одинаково?

   <details>
   <summary>Ответ</summary>

   Запрос использует индекс по выражению, только если выражение совпадает с
   индексным; `on conflict (...)` находит индекс по тому же выражению. С другим
   выражением поиск не использует индекс, а `on conflict` падает с ошибкой, что
   подходящего ограничения нет.
   </details>
