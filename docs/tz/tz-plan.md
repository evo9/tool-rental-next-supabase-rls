# Учебный проект: система проката инструмента

**Next.js (App Router) + Supabase, RBAC и RLS на уровне БД**

## 1. Цель

Освоить:

- Supabase как платформу: Auth, Storage, миграции через CLI, локальный запуск;
- Row Level Security в Postgres: политики на чтение и запись, `USING` против `WITH CHECK`;
- RBAC на уровне базы: три роли, матрица прав, реализованная политиками, а не проверками на фронте;
- Next.js App Router с серверной сессией Supabase.

Побочная цель - публичный репозиторий как пример под частый тип заказов «Supabase + RLS + операторская панель».

**Что не является целью:** дизайн, онлайн-оплата, личный кабинет клиента, мобильное приложение, мультиарендность. Домен взят простой намеренно - время должно уходить на инструмент, а не на предметную область.

## 2. Стек

- Next.js 15, App Router, TypeScript
- `@supabase/supabase-js` + `@supabase/ssr` (серверная сессия через куки)
- Supabase CLI, локальный стек в Docker (`supabase start`), облачный проект для демо
- Tailwind
- Миграции - только SQL-файлы в `supabase/migrations`, никаких изменений схемы через веб-интерфейс

Стартер-киты с готовой авторизацией не использовать. Весь Auth-флоу писать самому.

## 3. Домен

Точка проката инструмента. Оператор выдаёт клиенту несколько физических единиц, фиксирует состояние, принимает возврат целиком или частями, система считает стоимость аренды и просрочку.

### Роли

| Роль | Что может |
|---|---|
| OPERATOR | видеть клиентов и инструмент, создавать аренды, принимать возвраты |
| MANAGER | всё то же + заводить инструмент, менять тарифы, списывать единицы |
| SUPERADMIN | всё + управление сотрудниками и их ролями, просмотр аудит-лога |

### Таблицы

- `staff` - сотрудник: `user_id` (ссылка на `auth.users`), имя, `role`, `is_active`
- `customers` - клиент: ФИО, телефон, категория (`PLATINUM` / `GOLD` / `SILVER` / `NON_GRATA`), путь к фото
- `tools` - модель инструмента: название, тариф за сутки, залоговая стоимость
- `tool_units` - физическая единица: ссылка на `tools`, инвентарный номер, `status` (`AVAILABLE` / `RENTED` / `UNAVAILABLE` / `WRITTEN_OFF`)
- `rentals` - аренда: клиент, оператор, дата выдачи, плановая дата возврата, статус
- `rental_items` - единица в аренде: ссылка на `tool_units`, фактическая дата возврата, пути к фото выдачи и возврата, рассчитанная сумма
- `audit_log` - таблица, кто, что и когда изменил

Категория клиента влияет на grace period: сколько часов просрочки не тарифицируется.

## 4. Этапы

Каждый этап заканчивается рабочим состоянием, которое можно закоммитить.

### Этап 0. Поднять и осмотреться

Поставить Supabase CLI, выполнить `supabase init` и `supabase start`. Открыть Studio на локальном порту.

Посмотреть и понять, что именно поднялось: схемы `public`, `auth`, `storage`, какие контейнеры запущены, что лежит в `auth.users` после регистрации тестового пользователя, как выглядит anon-ключ и service_role-ключ и чем они отличаются.

Готово, когда: локальный стек поднимается одной командой, а ты можешь объяснить, зачем в проекте два ключа.

### Этап 1. Одна таблица и первая политика

Миграция создаёт `tools`. Включить RLS. Написать две политики: любой залогиненный читает, никто не пишет.

```sql
alter table public.tools enable row level security;

create policy "authenticated can read tools"
on public.tools for select
to authenticated
using (true);
```

Собрать страницу входа и список инструмента на Next.js. Сессия через `@supabase/ssr`, чтение данных в серверном компоненте.

Проверить обязательно: открыть тот же запрос без сессии (anon-ключом через `curl` в PostgREST) и убедиться, что возвращается пустой массив, а не ошибка. Это важная деталь - RLS не запрещает запрос, он просто не отдаёт строки.

Готово, когда: логин работает, список виден только после входа.

### Этап 2. Роли

Таблица `staff` с ролью. При регистрации сотрудника строка создаётся триггером на `auth.users` либо руками суперадмином - выбрать один вариант и обосновать в README.

Ключевой вопрос этапа: где политика берёт роль. Два подхода, разобрать оба.

**Подход А: роль лежит в таблице.** Политика делает подзапрос в `staff`. Просто, роль меняется мгновенно, но подзапрос выполняется на каждую строку, и легко получить рекурсию, если на `staff` тоже висит политика, которая читает `staff`. Лечится вспомогательной функцией:

```sql
create or replace function public.current_role()
returns text
language sql
stable
security definer
set search_path = public
as $$
  select role from public.staff where user_id = auth.uid() and is_active
$$;
```

`security definer` означает, что функция выполняется с правами владельца и обходит RLS на `staff`; `stable` позволяет планировщику вызвать её один раз на запрос, а не на каждую строку.

**Подход Б: роль лежит в JWT.** Через Custom Access Token Hook Supabase кладёт роль в токен, политика читает её из `auth.jwt()`. Подзапроса нет вообще, но роль обновляется только после перевыпуска токена, то есть понижение прав срабатывает не сразу.

Реализовать А как основной, Б описать в README как альтернативу и объяснить компромисс.

Дальше написать политики по матрице прав: оператор читает `tools`, менеджер вставляет и обновляет, суперадмин удаляет. Здесь впервые появляется `WITH CHECK` - выражение, которое проверяет не старую строку, а ту, что пытаются записать.

Готово, когда: три тестовых пользователя с разными ролями получают разный результат на одних и тех же действиях, и это проверено запросами, а не глазами в интерфейсе.

### Этап 3. Клиенты и приватный Storage

Таблица `customers` плюс загрузка фото клиента.

Создать **приватный** бакет. Фото документа - персональные данные, публичный бакет здесь недопустим. Загрузка идёт с клиента напрямую в Storage, поэтому доступ тоже регулируется политиками, но уже на таблице `storage.objects`:

```sql
create policy "staff can upload customer photos"
on storage.objects for insert
to authenticated
with check (
  bucket_id = 'customer-photos'
  and public.current_role() in ('OPERATOR','MANAGER','SUPERADMIN')
);
```

Показ фото - через signed URL с коротким сроком жизни, сгенерированный на сервере.

Готово, когда: файл из приватного бакета нельзя открыть по прямой ссылке, а в интерфейсе он показывается.

### Этап 4. Аренда: выдача и возврат

Создание аренды с несколькими единицами, фото на каждую, частичный возврат.

Главное техническое место этапа - запрет выдать одну единицу дважды. Не полагаться на проверку в коде, поставить ограничение в базе. Частичный уникальный индекс по активным позициям:

```sql
create unique index rental_items_active_unit
on public.rental_items (tool_unit_id)
where returned_at is null;
```

Смену статуса `tool_units` делать триггером от `rental_items`, чтобы статус нельзя было рассинхронизировать из приложения.

Готово, когда: две параллельные попытки выдать одну единицу дают ошибку уникальности, а не две аренды.

### Этап 5. Тариф и просрочка

Расчёт суммы: сутки аренды по тарифу модели, сверху просрочка с учётом grace period по категории клиента.

Расчёт писать функцией в Postgres и вызывать через RPC. Причина: расчёт денег не должен зависеть от того, какой клиент дергает API. Функция `security invoker` по умолчанию, то есть RLS внутри неё продолжает работать - убедиться в этом отдельным тестом.

Готово, когда: есть набор SQL-проверок на граничные случаи - возврат в тот же день, возврат минута в минуту по плану, просрочка внутри grace period, просрочка за его пределами.

### Этап 6. Аудит-лог

Триггер `after insert or update or delete` на ключевых таблицах пишет в `audit_log`: кто (`auth.uid()`), что, старое и новое значение в `jsonb`.

Политика на `audit_log`: читает только SUPERADMIN, пишет только триггер. Вставка из приложения должна быть запрещена всем - это проверяется отдельно.

Готово, когда: оператор не может ни прочитать лог, ни подделать запись в нём.

### Этап 7. Дашборд и импорт

Счётчики доступно / выдано / недоступно / активные аренды. Импорт списка инструмента из CSV - разбор на сервере, вставка пачкой, отчёт об ошибочных строках.

QR-код на единицу: генерация и страница печати наклеек. Сканирование камерой - опционально, в конце.

### Этап 8. Проверка политик и README

Отдельная папка со скриптами, которые логинятся тремя тестовыми пользователями и прогоняют матрицу прав: каждое действие каждой ролью, ожидаемый результат - разрешено или пусто. Это и есть доказательство, что RLS работает, и самая ценная часть репозитория для показа заказчику.

## 6. Правила работы над проектом

1. **SQL пишет Claude и тщательно документирует.** Миграции, политики, функции, триггеры генерируются, но каждый файл должен читаться без внешних объяснений. Обязательный минимум:
   - **шапка миграции**: этап, что делает миграция, от каких предыдущих миграций зависит, как проверить результат;
   - **каждая политика**: комментарий над ней - какая роль, какая операция, что проверяет `USING` (существующая строка) и что `WITH CHECK` (записываемая строка), почему именно так; какая роль и каким запросом должна получить пусто или ошибку;
   - **каждая функция**: зачем она, почему `security definer` или `security invoker`, почему `stable` / `volatile`, зачем зафиксирован `search_path`;
   - **каждый триггер**: когда срабатывает (`before` / `after`, на какие операции), какой инвариант держит и что сломается без него;
   - **ограничения и индексы с бизнес-смыслом** (частичные уникальные, `check`): какое правило домена они защищают;
   - `comment on table` / `comment on column` для таблиц и неочевидных колонок - описание видно в Studio.

   SQL не применяется и не коммитится, пока я его не прочитал и не понял. Непонятное разбирается вопросами до коммита, выводы - в `docs/rls-notes.md`.
2. **Обвязка генерируется целиком**: формы, таблицы, стили, компоненты UI.
3. **Ни одной политики без негативной проверки.** К каждой политике сразу идёт проверка, что другая роль получает пусто или ошибку.
4. `service_role` ключ не должен попадать в клиентский бандл ни при каких обстоятельствах. Проверить сборкой, поиском по `.next`.
5. Схему менять только миграциями. Правки через Studio не воспроизводятся у другого разработчика.
6. Seed-файл обязателен: любой, кто клонирует репозиторий, должен получить трёх пользователей и данные одной командой.

## 8. Оценка времени

Ориентировочно 20-30 часов чистого времени. Распределение неравномерное: этапы 2-5 занимают больше половины, потому что там основное новое и основной объём разбора SQL. Этапы 1, 7 и почти весь интерфейс проходят быстро.
